# K3 跨机 FSM 仿真

<!-- TODO: 更新 FSM 通信图，补充 ControlStatus、FaultStatus 和双向 HMI 通信，移除 x86_64 only 限定。 -->

## 1. 验证目标

本流程验证“键盘输入 → HMI 指令 → FSM 状态切换 → RL 推理 → MuJoCo 仿真驱动 → 状态回传”的完整控制链路。PC 运行 `driver_runtime`，K3 板卡运行 `control_runtime` 与 `hmi_runtime`，三者通过 UDP 通信。以下以 Unitree G1 为例。

## 2. 硬件与网络

| 设备 | 用途 |
| --- | --- |
| x86_64 PC，Ubuntu 22.04 或 24.04 | 运行 MuJoCo 与 `driver_runtime` |
| SpacemiT K3 COM260-KIT | 运行 `control_runtime`、`hmi_runtime` 与 RL 推理 |

PC 与 K3 需处于同一网段并可互相 `ping` 通。

## 3. 环境与策略模型

PC 与 K3 均需完成[安装与构建](../3.4.2-开发基础/3.4.2.1-安装与构建.md)。首次使用时，在 K3 板卡上下载对应机型的策略模型：

```bash
source build/envsetup.sh
download_models_g1.sh
```

每款机型的 `download_models_<robot>.sh` 脚本会在编译对应 target 后安装到 `output/staging/bin/`。脚本将该机型的 RL 策略模型下载到对应机型目录的 `policy/` 下。

## 4. 配置 UDP

在 `application/native/humanoid_unitree_g1/config/g1.yaml` 中设置 `transport.type: "udp"`，并填写 PC 与 K3 的实际 IP：

```yaml
transport:
  type: "udp"
  udp:
    driver_ip: "192.168.1.100"   # PC 的 IP
    control_ip: "192.168.1.200"  # K3 板卡的 IP
    hmi_ip: "192.168.1.200"      # HMI 所在设备，本例也是 K3
    state_port: 8800            # driver → control
    control_port: 8801          # control → driver
    hmi_port: 8802              # hmi → control
    status_port: 8803           # control → hmi
```

PC 和 K3 使用相同的端点配置，并放行相应 UDP 端口。各端须使用相同的 transport 协议版本；HMI 显示状态依赖 status 回传通道。

## 5. 启动进程

### 5.1 PC：启动仿真驱动

```bash
source build/envsetup.sh
run_driver_g1.sh
```

MuJoCo 窗口弹出后，检查终端中的自由度、仿真步频和 UDP 端点是否符合机型配置。

![MuJoCo 仿真窗口](../assets/fsm_driver.png)

### 5.2 K3：启动控制进程

在 K3 终端 1 运行：

```bash
source build/envsetup.sh
run_control_g1.sh
```

确认启动时默认策略的模型与 `model_io` 已预加载，初始状态为 `POWER_OFF`，策略与 `rl_policy.onnx_infer.default_policy` 一致，driver 状态持续更新且没有通信超时或锁存故障。切换策略后需等待模型准备完成，再进入 HOME；进入 RL 后检查实际推理频率。

### 5.3 K3：启动 HMI

在 K3 终端 2 运行：

```bash
source build/envsetup.sh
run_hmi_g1.sh
```

HMI 从 Control 回传读取真实 FSM、当前策略、速度和故障状态。发送请求后应等待状态回传确认；界面显示的“已请求”不表示切换已经完成。

## 6. HMI 操作

<!-- TODO: 替换 HMI 主页面和策略选择页面截图，包含 HOME、真实状态回传及故障确认。 -->

| 按键 | 功能 |
| --- | --- |
| 主页面 `→` / `←` | 请求前进到下一状态 / 返回安全的前级状态 |
| `o` → `h` → `z` → `r` | 兼容快捷键，依次请求 DAMP、HOME、ZERO、RL |
| `p` | 打开策略选择页；用 `↑/↓` 或 `k/j` 选择，`Enter` 确认 |
| `v` / `Enter` | 在 RL 状态且心跳正常时进入速度控制页；策略需配置 `command.limits` |
| `f` | 请求 POWER_OFF，等待回传确认失能状态 |
| 速度页 `w/s`、`a/d`、`q/e` | 分别增减 vx、vy、wz，范围由当前策略的 `command.limits` 约束 |
| 速度页 `v` / `Esc` | 退出速度页并清零速度 |
| `空格` | 速度清零 |
| `x` | 在 POWER_OFF 下确认已经解除的锁存故障 |

只有 `POWER_OFF` 或 `DAMP` 且无锁存故障时才接受人工切换策略。HMI 候选列表优先取自 `rl_policy.onnx_infer.policy_names`，策略参数定义在 `policies` 中。

HOME 平滑恢复到 `robot_base.default_joint_pos`，完成后才允许进入 ZERO。ZERO 优先使用策略的 `zero_target_pos`，未配置时使用 `rl_default_pos`；增益优先取 `behavior_manager.zero.kp/kd`，未配置时兼容使用当前策略的增益。ZERO 满足位置、速度和持续稳定条件后才允许进入 RL。

若目标策略在 YAML 中配置了 `prerequisite: { policy, duration }`，例如 dance 或 kungfu 配置 stand 2 秒，`behavior_manager` 会先运行前置策略，达到指定时长后再切换目标策略。

故障会阻止再次上电。排除故障后先回到 `POWER_OFF`，再按 `x` 并等待确认；仍在发生的故障不能清除，恢复要求见[运行时通信与安全](../3.4.2-开发基础/3.4.2.3-运行时通信与安全.md#5-安全边界)。

## 7. 运行结果

MuJoCo 窗口打开后，机器人处于悬挂保护中。按 `o` → `h` → `z` → `r` 逐级请求状态切换，等待 HOME 完成和 ZERO 到位。以 `walk_mjlab` 为例，进入 RL 后应能零速度站立，并在速度页响应允许范围内的命令；动作跟踪策略按对应参考动作验证。

`driver_runtime` 根据控制端发送的 `ControlMode` 自动管理悬挂保护：进入 `RL` 时取消悬挂，回到 `POWER_OFF` 时重新启用。MuJoCo 窗口内的 `F` 键可手动切换悬挂，`↑/↓` 调节高度，`R` 重置高度；这些按键与 HMI 终端的按键分别生效。

若仿真机器人摔倒或偏离准备姿态，应先返回 POWER_OFF，恢复悬挂并检查故障，再按 HOME、ZERO、RL 的进入条件重新运行。
