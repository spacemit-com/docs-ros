# 运行时架构与接口

<!-- TODO: 重绘 RL 数据流图，区分 YAML/model_io、观测历史、ONNX Runtime/MNN 推理与 feedback、动作处理与上层 PD 控制。 -->

RL 组件位于 [`components/model_zoo/rl`](https://github.com/spacemit-com/model_zoo_rl)，负责把机器人状态和外部输入转换为模型输入，并将模型输出处理为关节目标位置。组件不依赖具体机器人型号，机型差异由上层提供的模型、YAML 和关节映射描述。

## 1. 组件边界

```text
ONNX / MNN 模型 + YAML 策略契约
                 │
                 ▼
       配置解析 / 张量绑定
                 │
机器人状态 ─► 观测组装 ─┐
外部输入 ───────────────┼─► ONNX Runtime / MNN ─► action / expose / feedback
常量与反馈状态 ─────────┘                               │
                                                      ▼
                                        裁剪与平滑 ─► 关节动作映射
```

主要代码位置如下：

```text
components/model_zoo/rl/
├── include/rl_service.h              # 公共数据结构和 C++ API
├── src/policy_config_loader.cpp      # YAML 策略配置解析
├── src/policy_executor.cpp           # 观测、推理和动作处理编排
├── src/obs_*.{h,cpp}                 # 观测项与历史组装
├── src/backends/onnx/onnx_infer.{h,cpp}  # ONNX Runtime 后端
├── src/backends/mnn/mnn_infer.{h,cpp}    # MNN 后端，默认编入
├── example/                          # 功能测试与 benchmark
└── scripts/                          # benchmark wrapper 和模型辅助工具
```

## 2. 调用流程

对外头文件为 `include/rl_service.h`，链接库为 `librl.so`。

```cpp
#include "rl_service.h"
using namespace rl_policy;

// 1. 按策略名加载 YAML
LoadedPolicyConfig loaded_cfg =
    LoadPolicyConfigFromYaml(yaml_path, policy_name, robot_dir);

// 2. 初始化模型、张量绑定和观测组装器
PolicyExecutor policy;
policy.Init(loaded_cfg.exec_cfg);

// 3. 每个推理周期组装观测
Eigen::VectorXf obs;
policy.AssembleObs(gyro, rpy, cmd_vx, cmd_vy, cmd_wz,
                   joint_pos, joint_vel, base_quat, base_vel, dt, obs);

// 4. 推理并映射为全身关节目标位置
std::vector<double> action;
policy.Infer(obs, action);

std::vector<double> target_pos;
policy.MapActionToTargetPos(action, target_pos);
```

`PolicyExecutor` 不使用 `kp`、`kd`，也不负责把关节目标发送给机器人。配置加载器会将这些控制参数放入 `LoadedPolicyConfig`，由上层控制运行时使用。

## 3. 公共接口

| 接口 | 说明 |
| --- | --- |
| `LoadPolicyConfigFromYaml(yaml, name, robot_dir)` | 从 `rl_policy.onnx_infer.policies.<name>` 加载策略，返回执行器配置和上层控制参数 |
| `Init(cfg)` | 按 `backend` 加载 ONNX 或 MNN 模型，建立并校验全部 named tensor binding |
| `ObsDim()` / `ActionDim()` | 查询观测与动作维度 |
| `FeedbackStateCount()` / `HasObsHist()` | 查询自动反馈张量数量和模型级观测历史输入 |
| `GetRuntimeInfo()` | 查询实际初始化的 provider、线程和 SpaceMIT EP 状态 |
| `PrintModelInfo()` | 输出模型输入输出张量的名称、shape 和数据类型 |
| `SetCustomScalar(...)` / `GetCustomScalar(...)` | 写入或读取上层计算的自定义标量观测 |
| `SetCustomArray(...)` | 向观测项注入上层计算的数组 |
| `SetModelInput(...)` | 设置 `source: external` 的模型输入，支持 float 数组或原生 `TensorView` |
| `GetModelOutput(...)` / `GetModelOutputTensor(...)` | 读取 `target: expose` 的最近一次模型输出 |
| `AssembleObs(...)` | 按段计算、处理并拼接观测 |
| `Infer(obs, action)` | 按 `model_io` 绑定输入、执行推理和反馈回灌，返回裁剪及平滑后的动作 |
| `Infer(obs, action, &raw_action)` | 在返回处理后动作的同时，取得模型 action 的原始输出 |
| `RequestInferenceTermination()` | 请求中断当前推理，供上层停止异步推理线程使用；调用方仍须等待推理线程退出 |
| `ClearInferenceTermination()` | 推理线程退出后清除中断请求，继续使用已初始化的模型；不得与 `Infer` 并发调用 |
| `MapActionToTargetPos(...)` | 将动作按关节索引映射为全身目标位置 |

完整定义和示例见 [C++ 对外头文件](https://github.com/spacemit-com/model_zoo_rl/blob/main/include/rl_service.h) 与 [策略执行器示例](https://github.com/spacemit-com/model_zoo_rl/blob/main/example/test_policy_executor.cpp)。

## 4. 推理后端

### 4.1 模型引擎

策略的 `backend` 选择模型引擎，省略时为 `onnx`：

| `backend` | 模型文件 | `runtime.provider` |
| --- | --- | --- |
| `onnx` | `.onnx` | `auto`、`cpu` 或 `spacemit`，默认 `auto` |
| `mnn` | `.mnn` | `auto` 或 `cpu`，在 CPU 上推理 |

两种引擎共用 `model_io`、观测组装、feedback 和动作映射，更换引擎不需要修改上层控制代码。MNN 默认编入，构建选项见[快速开始](4.3.1-快速开始.md#mnn-后端)；产物未编入 MNN 时，`backend: mnn` 的策略在 `Init` 阶段报错。

ONNX 后端在 x86_64 上的 `auto` 使用 CPU provider；RISC-V 上的 `auto` 会尝试注册 SpaceMIT EP，初始化失败时回退 CPU。显式请求 `spacemit` 时，EP 初始化失败会直接报错。EP 注册成功仍不代表全部算子都已分配给 EP，实际 provider 状态以 `GetRuntimeInfo()` 和程序日志为准，算子覆盖情况应通过 EP 子图导出确认。

### 4.2 运行参数

YAML 加载器解析策略节点下的 `backend` 和 `runtime`，例如在 `rl_policy.onnx_infer.policies.<name>` 下配置：

```yaml
backend: onnx
runtime:
  provider: auto
  threads: 2
  warmup_runs: 1
  ort_spinning: false
  affinity: "4"
  worker_sched: fifo
  worker_priority: 55
```

示例数值需按板端的核心分配和实测负载调整。

| 参数 | 默认值 | 说明 |
| --- | --- | --- |
| `threads` | `1` | ONNX CPU 后端的 intra-op 线程数，包含调用推理的线程；SpaceMIT EP 的请求线程数；MNN 的推理线程数。该参数本身不绑核 |
| `warmup_runs` | `0` | 策略接管前用配置的输入初值预跑的次数，用于初始化后端缓存；预热结果不更新 feedback、动作或观测历史。模型不接受初始输入时不要启用 |
| `ort_spinning` | `true` | ONNX Runtime worker 在两次推理之间是否忙等；与控制、通信线程共用 CPU 时设为 `false` |
| `affinity` | 空 | ONNX CPU 后端：worker 使用的 Linux CPU 编号（从 0 开始），可写一组（如 `"0,3,4"`、`"3-4"`）由全部 worker 共用，或按 `threads-1` 组逐个指定。SpaceMIT EP：原样作为 EP 线程列表（如 `"0;1"`） |
| `worker_sched`、`worker_priority` | 继承 | ONNX CPU worker 的调度策略（`other`、`fifo` 或 `rr`）和优先级 |
| `ep_options` | 空 | 传给 SpaceMIT EP 的字符串键值，如算子过滤或精度选项；只在注册 EP 时使用，CPU 会话忽略 |

调用推理的线程不受这些 worker 参数影响，由上层应用配置，人形运行时使用 `robot_base.threads.rl_infer`。未设置 `worker_sched` 时，worker 继承创建会话那个线程的 CPU 集合和调度；上层在后台线程加载模型时，worker 不会自动获得之后推理线程的实时优先级。请求的实时优先级超出系统允许范围时，组件记录警告并改用 `other/0`，非特权的仿真环境仍可运行。`worker_sched` 和 `worker_priority` 不作用于 SpaceMIT EP 的线程。

显式的 `threads`、非空 `affinity` 及启用的 dump/profile 设置优先于同名 EP 选项；`ep_options` 的键及取值由所用 EP 版本解释。只应在注册 EP 时生效的设置（例如 EP 线程亲和性）可以写在 `ep_options` 中，CPU 会话忽略这些键，同一份 YAML 在 x86_64 仿真中不受影响。MNN 使用 `provider`、`threads` 和 `warmup_runs`，配置 `affinity`、`worker_sched`、`worker_priority` 或 EP 相关选项时初始化失败。

会话创建后，日志输出新起线程的实际 CPU 与调度（`worker threads=tid@cpus/policy/priority`），`GetRuntimeInfo()` 返回请求和实际初始化的 provider。多线程是否有益应在实际负载下测量，不能只依据单次推理基准。

`ep_dump_subgraphs` 和 `ep_profile_prefix` 不由 YAML 解析，需要时在 C++ 中通过 `loaded_cfg.exec_cfg.runtime` 于 `Init` 前设置。Benchmark 工具另按命令行参数设置运行选项，见[模型验证与性能评测](4.3.4-模型验证与性能评测.md#4-benchmark-工具与方法)。

## 5. 状态生命周期

一个 `PolicyExecutor` 实例会持续保存观测段历史、`observation_history`、feedback 张量、external 输入、最近一次 expose 输出和动作平滑状态。

- feedback 可由配置值初始化；未提供初值时使用零缓冲，之后由绑定的模型输出自动回灌。
- external 输入设置后持续有效，未配置默认值时必须在首次 `Infer` 前由上层设置。
- `GetModelOutputTensor()` 返回的 view 指向内部缓冲区，有效期到下一次 `Infer`。
- 重建执行器会清空上述运行状态；切换策略时应重新加载配置并初始化新实例。
- `RequestInferenceTermination()` 用于停止阶段，不是暂停接口，也不保证在固定时限内完成取消。上层须等待推理线程结束；之后调用 `ClearInferenceTermination()` 可继续使用同一会话，不必重新加载模型。清除中断请求不会重置观测历史、feedback 等运行状态；需要从初始状态开始时重新 `Init()`。

策略选择、切换时机、前置策略链、控制增益下发和异常处置属于上层行为管理职责，不由 RL 组件调度。配置字段及张量契约见[策略配置与模型契约](4.3.3-策略配置与模型契约.md)。
