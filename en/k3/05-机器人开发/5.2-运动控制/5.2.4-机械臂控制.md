# Motion Control · Robot Arm Control

## 1. Overview

The `manipulator` component provides a unified robot arm control C API that abstracts away low-level hardware differences and provides calling code with capabilities such as robot arm instance creation, joint motion, linear motion, target pose control, state retrieval, and teaching mode switching. The component currently supports the HuggingFace open-source [SO-101 robot arm](https://huggingface.co/docs/lerobot/en/so101#so-101) UART driver and can be extended to other robot arm devices through its plugin mechanism.

### Features

This module provides the following capabilities:

- Offers a pure C interface for easy reuse in C/C++ projects or higher-level services;
- Supports joint-space motion (PTP / MoveJ), Cartesian target pose solving, and linear motion (MoveL, requires IK/FK solver);
- Supports runtime binding of kinematics solvers; currently available backends are `dummy` and `pinocchio`;
- Supports SO-101 5-DOF robot arm control, with joint angles in `rad` and end-effector positions in `m`;
- Higher-level code can advance the control loop by calling `manip_tick()` periodically at a high frequency; a control rate of approximately 200 Hz is recommended;
- Supports a calibration process, including zero-offset and travel range recording;
- Supports hardware tests, kinematics tests, and dummy-driver unit tests.

| Item | Details |

| Basic Dependencies | `pthreads`, `libm` |

#### Permission Setup

The UART device on the K3 board typically appears as `/dev/ttyACM0`. Run the following command to grant read/write access to the robot arm:

```bash
sudo chmod 666 /dev/ttyACM0
```

Before powering on for the first time, confirm cable connections, power supply capacity, and robot arm mounting to avoid collisions.

### Build

Enter the module's code directory and build:

```bash
cd components/control/manipulator
mkdir build && cd build
cmake ..
make -j$(nproc)
```

By default, this generates `libmanipulator.so` and copies `urdf/` to the build directory.

To fully enable the SO-101 driver and Pinocchio kinematics, run:

```bash
cd components/control/manipulator
rm -rf build && mkdir build && cd build
cmake .. -DMANIP_BUILD_HW_TEST=ON
make -j$(nproc)
```

Typical artifacts include:

| Artifact | Description |
| --- | --- |
| `build/libmanipulator.so` | Robot arm control shared library |
| `build/test_manipulator` | Dummy driver unit test |
| `build/test_kinematics` | Kinematics test program |
| `build/test_hw_so101` | SO-101 hardware test program (requires `MANIP_BUILD_HW_TEST`) |

Build option descriptions:
- `MANIP_ENABLE_SO101_DRIVER=ON`: Enables the SO-101 UART driver;
- `MANIP_ENABLE_PINOCCHIO=ON`: Enables the Pinocchio kinematics solver; Pinocchio must be compiled first;
- `MANIP_BUILD_TESTS=ON`: Enables basic unit tests;
- `MANIP_BUILD_HW_TEST=ON`: Compiles the SO-101 hardware test program;
- If the `motor` component headers are not found, the SO-101 driver is automatically disabled; if `pinocchio` is not found, the corresponding kinematics features will be unavailable.

## 3. Example Usage

### 3.1 Example 1: Basic Framework and Kinematics Verification

**Prerequisites**: See Section 2. This example does not require connecting a real robot arm. `pinocchio` is enabled by default and its dependencies must be installed and built first.

**Step 1**: Compile `pinocchio` from source.

```bash
# Install build dependencies
sudo apt install -y cmake build-essential libeigen3-dev libboost-all-dev liburdfdom-dev

# Clone and build
git clone --recursive -b v3.9.0 https://github.com/stack-of-tasks/pinocchio.git
cd pinocchio
mkdir build && cd build
cmake .. \
    -DCMAKE_BUILD_TYPE=Release \
    -DCMAKE_INSTALL_PREFIX=/usr/local \
    -DBUILD_PYTHON_INTERFACE=OFF \
    -DBUILD_TESTING=OFF \
    -DBUILD_WITH_COLLISION_SUPPORT=OFF
make -j$(nproc)
sudo make install
sudo ldconfig
```

**Step 2**: Enter the module directory and compile the test programs.

```bash
cd components/control/manipulator
rm -rf build && mkdir build && cd build
cmake ..
make -j$(nproc)
```

On success, the build produces the robot arm test program `test_manipulator` and the kinematics test program `test_kinematics`:


> [!NOTE]
>

> 2. Always run the assemble and calibration process first to explore the arm's reachable limits; moving without calibration risks motor damage.
> 3. For SO-101 joint naming conventions, see the LeRobot open-source community documentation: [https://huggingface.co/docs/lerobot/en/so101#so-101](https://huggingface.co/docs/lerobot/en/so101#so-101).

## 4. Application Development

#### External API or Interface

- Public header file: `components/control/manipulator/include/manipulator.h`
- Kinematics interface header: `components/control/manipulator/include/kinematics_interface.h`
- Dynamic library artifact: `libmanipulator.so`
- Common interfaces include:
  - `manip_alloc()` / `manip_free()`: Create and release robot arm instances
  - `manip_move_joints()`: Joint-space motion control
  - `manip_move_line()`: Cartesian-space linear motion control
  - `manip_move_target()`: Target pose motion control
  - `manip_solve_target_joints()`: Run inverse kinematics only, without issuing motion commands
  - `manip_get_state()`: Get joint state and end-effector pose information
  - `manip_set_kinematics()`: Bind FK / IK solver
  - `manip_tick()`: Periodically advance the control state machine

#### Usage Notes

- Create a robot arm instance with `manip_alloc("so101", &cfg)`, where `cfg` can configure the serial port path, baud rate, servo IDs, URDF path, and kinematics solver name;
- Call `manip_free()` to release resources when the robot arm instance is no longer needed;
- If the application requires end-effector pose retrieval or MoveL control, bind a kinematics solver first; otherwise those interfaces may return `MANIP_ERR_NOSYS`;
- `manip_move_line()` calls the driver's native implementation first; if the current driver does not provide this capability, it automatically falls back to an "IK → MoveJ" control flow;
- For real-time control, call `manip_tick(dev, dt_s)` at a high frequency to continuously send trajectory points or motion commands;
- When running hardware control, pay close attention to serial port permissions, power supply capacity, and the robot arm's safe motion range;
- After a kinematics solver is bound, its lifetime and ownership are taken over by `manip_dev`; the application must not release it manually.

## 5. Debugging Guide

- Run `test_manipulator` first to verify driver registration and the basic framework, then run `test_kinematics` to verify the URDF and kinematics pipeline, and finally connect real hardware and run `test_hw_so101`, troubleshooting layer by layer in "software → algorithm → hardware" order.
- If the build log shows `Pinocchio not found`, the FK/IK backend is not enabled; check whether `pinocchio` is installed correctly and run `sudo ldconfig` to update the library cache.
- If `manip_alloc("so101", ...)` fails, check whether the `motor` component headers and library are compiled and linked correctly, and whether the CMake output shows `SO-101 driver enabled`.
- If the robot arm is unresponsive, check:
	- Whether the serial node is correct;
	- Whether serial port permissions have been opened;
	- Whether the baud rate is the default 1000000;
	- Whether the servo IDs are 1–5;
	- Whether the power supply provides sufficient current.
- If the zero position is inaccurate after calibration, re-run the calibration process, confirm each joint is at the exact center position during calibration, and verify the calibration file was saved correctly.
- When coordinating with hardware or driver engineers, provide the following information:
	- Serial device node and permission status;
	- Servo IDs, baud rate, and power specifications;
	- Build options used (whether `MANIP_ENABLE_SO101_DRIVER` / `MANIP_ENABLE_PINOCCHIO` were enabled);
	- Test program output logs;
	- Whether unit tests, kinematics tests, and hardware tests can each be completed independently.

## 6. Troubleshooting

| Symptom | Possible Cause | Solution |
| --- | --- | --- |
| Build fails with `pinocchio` not found | `pinocchio` not installed, or installation path not in default search path | Build and install `pinocchio` from source following the module README, run `sudo ldconfig`, and if necessary specify the install path via `-DCMAKE_PREFIX_PATH` |
| `manip_alloc("so101", ...)` returns null | SO-101 driver not compiled into the library, or `motor` headers not found | Check CMake output to confirm `MANIP_ENABLE_SO101_DRIVER=ON` and `motor` component is visible |
| Hardware test reports connection failure | Serial node incorrect, insufficient permissions, baud rate mismatch, or servo not powered | Check `/dev/ttyACM*` / `/dev/ttyUSB*`, open permissions, and confirm 1 Mbaud and servo power are correct |
| `manip_move_line()` returns not implemented | Kinematics solver not bound, or current driver does not implement MoveL | Call `manip_set_kinematics()` to bind a solver first, or switch to `manip_move_joints()` |
| Large zero-position error after calibration | Joint was not at the exact center position during calibration, or calibration file was not saved correctly | Re-run the calibration process, confirm the center pose is accurate, and verify the calibration file |
