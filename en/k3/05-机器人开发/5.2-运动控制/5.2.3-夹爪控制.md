# Motion Control · Gripper Control

## 1. Overview

The `grasp` component provides a unified end-effector control C API that abstracts away low-level hardware differences and provides calling code with capabilities such as gripper instance creation, grab/release control, fine position control, state feedback, load detection, and interactive calibration. The component currently supports the SO-101 gripper UART driver and can be extended to other end effectors such as claw grippers and suction cups through its driver plugin mechanism.

### Features

This module provides the following capabilities:

- Offers a pure C interface for easy reuse in C/C++ projects or higher-level services;
- Supports three basic control commands, `GRAB`, `RELEASE`, and `RELAX`, along with fine position control via `grasp_set_position()`;
- Includes a built-in five-state state machine (`IDLE`, `MOVING`, `HOLDING`, `EMPTY`, `ERROR`) with automatic transitions based on position and load;
- Supports position mapping control based on a normalized opening range `[0.0, 1.0]`, where `0.0` means fully closed and `1.0` means fully open;
- Supports single-servo SO-101 gripper control, using the Feetech STS3215 servo by default, with default ID `6` and default baud rate `1000000`;
- Supports an interactive calibration process that learns the actual hardware opening and closing limits and persists the calibration results to a local configuration file;
- Higher-level code can advance the state machine and refresh feedback by calling `grasp_tick()` periodically at a high frequency, making it suitable for coordinated use with the robot arm control module;
- Supports dummy-driver unit tests and SO-101 hardware interaction tests.

## 2. Environment Setup

### Prerequisites

#### Hardware and Connections

| Item | Details |
| --- | --- |
| Hardware Platform | SpacemiT K3 development board |
| End Effector | SO-101 gripper |
| Actuator | Feetech STS3215 servo |
| Communication | UART |
| Default Connection | `/dev/ttyACM0`, baud rate `1000000` |
| Power Requirements | The gripper servo requires a stable power supply; <br>a 7.4V battery or equivalent is recommended |

The gripper and the SO101 robot arm joints are controlled over a single bus and connected to the K3 development board via USB serial, as shown below:

![](assets/mars-connect.jpg)

#### Software Environment

| Item | Details |
| --- | --- |
| Operating System | Bianbu 3.0+ |
| Compilation Standard | C99 / C++14 |
| Basic Tools | `cmake`, `build-essential` |
| Basic Dependencies | `pthreads`, `libm` |
| Control Dependency | `components/peripherals/motor` |

#### Permission Setup

The SO-101 gripper typically communicates with the system through a serial device node (such as `/dev/ttyACM0`). Before running hardware tests, ensure the current user has serial port access permissions, for example:

```bash
sudo chmod 666 /dev/ttyACM0
```

Before powering on for the first time, confirm that the servo wiring, power capacity, and gripper mechanism are in good condition to avoid hardware damage from jamming or overload.

### Build

Enter the module's code directory and run the basic build:

```bash
cd components/control/grasp
mkdir build && cd build
cmake ..
make -j$(nproc)
```

By default, this generates `libgrasp.so` and the basic test program `test_grasp`.

To enable the SO-101 gripper hardware test program, run:

```bash
cd components/control/grasp
rm -rf build && mkdir build && cd build
cmake .. -DGRASP_BUILD_HW_TEST=ON
make -j$(nproc)
```

Typical artifacts include:

| Artifact | Description |
| --- | --- |
| `build/libgrasp.so` | Gripper control shared library |
| `build/test_grasp` | Dummy driver unit test program |
| `build/test_hw_so101_gripper` | SO-101 gripper hardware test program (requires `GRASP_BUILD_HW_TEST`) |

Build option descriptions:
- `GRASP_BUILD_TESTS=ON`: Enables basic unit tests;
- `GRASP_BUILD_HW_TEST=ON`: Compiles the SO-101 gripper hardware test program;
- If the `motor` component headers or library are not found, the SO-101 gripper driver and hardware test capabilities are automatically disabled.

## 4. Application Development

#### External API or Interface

- Public header file: `components/control/grasp/include/grasp.h`
- Dynamic library artifact: `libgrasp.so`
- Common interfaces include:
	- `grasp_alloc()` / `grasp_free()`: Create and release gripper instances
	- `grasp_execute()`: Execute `GRAB` / `RELEASE` / `RELAX` control commands
	- `grasp_set_position()`: Normalized position control
	- `grasp_get_state()`: Get the gripper's high-level state
	- `grasp_get_feedback()`: Get current position and load feedback
	- `grasp_tick()`: Periodically advance the state machine
	- `grasp_calibrate()`: Run the interactive calibration process

#### Usage Notes

- Create a gripper instance with `grasp_alloc("so101_gripper", &cfg)`, where `cfg` can configure the serial port path, baud rate, servo ID, and grab parameters;
- For logic-only verification, create a dummy driver instance with `grasp_alloc("dummy", NULL)`;
- `grasp_execute()` is suitable for high-level actions such as fully open, fully close, and relax; to control a specific opening degree, use `grasp_set_position()`;
- Call `grasp_tick(dev, dt_s)` at a fixed frequency to continuously send target commands, refresh feedback, and complete `HOLDING` / `EMPTY` state determination;
- The position returned by `grasp_get_feedback()` is a normalized value `[0.0, 1.0]`, and the load value is the raw feedback from the low-level servo;
- When connecting hardware for the first time, run `grasp_calibrate()` first so that the position mapping matches the actual mechanism limits;
- A gripper instance automatically runs `RELAX` before release, but during application exit or error recovery, it is still recommended to explicitly call `grasp_stop()` or `grasp_execute(dev, GRASP_CMD_RELAX, 0.0f)`;
- When running hardware control, pay close attention to serial port permissions, servo power capacity, and overload protection status.

## 5. Debugging Guide

- Run `test_grasp` first to verify driver registration, parameter checks, and basic state machine logic, then connect real hardware and run `test_hw_so101_gripper`, troubleshooting layer by layer in "software → hardware" order;
- If the build log shows `motor headers not found` or the hardware test program is not generated, the `motor` component was not detected correctly; check whether `components/peripherals/motor` has been compiled and can be detected by CMake;
- If `grasp_alloc("so101_gripper", ...)` fails, focus on checking the serial node, serial port permissions, baud rate, servo ID, and servo power status;
- If gripper movement is abnormal or positions are inaccurate, run the calibration process first and confirm that `./config/so101_gripper_calibration.json` has been generated correctly with valid content;
- If load detection is inaccurate, check whether the `hold_threshold` setting is appropriate and adjust the threshold based on the actual object being grasped;
- When coordinating with hardware or driver engineers, provide the following information:
	- Serial device node and permission status;
	- Servo ID, baud rate, and power specifications;
	- Whether `GRASP_BUILD_HW_TEST` was enabled;
	- Test program output logs;
	- Whether the calibration file exists, and the open/close ticks range obtained from calibration.

## 6. Troubleshooting

| Symptom | Possible Cause | Solution |
| --- | --- | --- |
| `test_hw_so101_gripper` not generated during build | `motor` component headers or library not found, hardware driver automatically disabled | Check whether `components/peripherals/motor` has been compiled; if necessary, specify paths via `MOTOR_INCLUDE_PATH` / `MOTOR_LIB_PATH` |
| `grasp_alloc("so101_gripper", ...)` returns null | Serial port inaccessible, servo not powered, or servo ID/baud rate mismatch | Check `/dev/ttyACM*` or `/dev/ttyUSB*` nodes, open permissions, and confirm the default 1 Mbaud and servo ID=6 configuration are correct |
| Gripper moves to the wrong position | Not calibrated, or the current hardware open/close range does not match the default mapping | Run the calibration process in `test_hw_so101_gripper` to generate and save a calibration file |
| Gripper does not enter `HOLDING` state after grabbing | Load threshold too high, or the grasped object is too light | Adjust the `hold_threshold` parameter and re-verify with the actual load |
| Calibration fails or range is abnormal | Manual positioning was inaccurate, or the difference between open and closed positions is too small | Re-run calibration, ensuring the fully open and fully closed positions are clearly different and the range exceeds the minimum valid threshold |
