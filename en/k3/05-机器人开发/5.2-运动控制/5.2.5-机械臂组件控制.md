# Motion Control · Robotic Arm Component Control

## 1. Module Overview

The `manipulation` component provides unified control of robotic arms and end effectors: device configuration selects the hardware, and a single set of commands or C++ / Python interfaces sends actions. Applications do not call vendor SDKs directly. Switching between already-adapted devices only requires a configuration change, and adding a new device only requires a new driver.

For a complete application example, see [Dice Game](../../03-参考方案/3.3-机械臂/3.3.4-摇骰子游戏.md).

Read the sections that match your task:

- Supported devices, software architecture, and code layout: [§1 Supported Devices](#supported-devices), [§1 Software Architecture](#software-architecture), [§1 Code Layout](#code-layout);
- Build and run examples without hardware: [§2 Environment Setup](#2-environment-setup), [§3.1 Example 1: Mock Joint Task](#31-example-1-mock-joint-task), [§3.2 Example 2: Python Mock Control](#32-example-2-python-mock-control);
- Control real hardware: the real-hardware examples in [§3 Examples](#3-examples), one section per device;
- Call from an application or integrate a new device: [§4 Application Development](#4-application-development);
- Troubleshoot and look up commands: [§5 Debugging Guide](#5-debugging-guide), [§6 Troubleshooting](#6-troubleshooting).

### Specifications

- **Device integration**: YAML-driven configuration, connection parameters, joint limits, and effector channels. A mock driver is provided for validation without hardware.
- **Motion control**: joint point targets, target following, continuous paths, timed trajectories, and multi-channel effector actions; the specific capabilities are declared by the driver. Effector positions are uniformly `0` for closed and `1` for open.
- **Execution safety**: device exclusivity, arrival verification, cancellation, timeouts, and fault latching. The component does not automatically enable devices, clear faults, home, or retry.
- **Kinematics**: URDF-based forward and inverse kinematics, supporting end-effector pose queries, pose motion, and Cartesian linear motion.
- **Tooling**: pose recording and state monitoring, eye-to-hand calibration, and SO101 servo parameter and center calibration.

### Supported Devices

| Driver | Device | Arm capabilities | End effector |
| --- | --- | --- | --- |
| `mock_device` | Software simulation | Point targets, following, paths, trajectories | Can simulate position feedback |
| `agx_nero_revo2` | Agilex Nero 7-axis, optional Revo2 right hand | Point targets, following, paths, trajectories | Revo2 six channels, no position feedback |
| `so101` | SO101 5-axis, optional stock gripper | Point targets, following, enable and disable | Single-channel position feedback, grasp determined by load |

### Software Architecture

![manipulation component architecture: the command line, YAML tasks, and Python interface reach device sessions through the local manipulation-device process, while C++ applications call directly; device sessions use each driver according to device.driver; the right side shows kinematics, hand-eye calibration, configuration and models, and SO101 servo tools](assets/manipulation-sdk-architecture.svg)

- **Invocation methods**: the command line and YAML joint tasks are for debugging and fixed sequences; the Python / C++ interfaces are for application development.
- **Device process `manipulation-device`**: the command line, YAML tasks, and Python interface all reach devices through it.
  - `run`: executes YAML tasks;
  - `serve`: acts as the local control process for the Python `DeviceClient`, communicating over a JSONL protocol;
  - `inspect` and similar: diagnostics.

  C++ applications bypass it and call device sessions directly in their own process after linking the component library.
- **Device session `DeviceSession`**: holds exclusive access to one device, executes actions and determines completion, and handles cancellation, timeouts, and faults. Every entry point ultimately executes through it, so safety checks, configuration, and returned results are consistent; an action validated from the command line behaves the same when moved into an application.
- **Drivers**: created according to `device.driver` in the configuration, responsible for hardware communication, and required to truthfully declare supported motion and feedback capabilities.
- **Supporting capabilities**: these do not participate in real-time control; they provide end-effector poses, joint targets, and camera extrinsics to applications.

### Code Layout

The source is in `components/control/manipulation`:

```text
manipulation/
├── include/manipulation/   # Public C++ interfaces
├── core/                   # Device session: exclusivity, execution, arrival verification, fault handling
├── runtime/                # Configuration parsing and YAML joint tasks
├── drivers/                # Drivers: arms/, effectors/, common/ (shared connections), mock/
├── capabilities/           # Features and command line
│   ├── motion/             #   manipulation-device and the local control process
│   ├── diagnostics/        #   manipulation operation commands
│   ├── kinematics/         #   Forward and inverse kinematics
│   └── calibration/        #   Pose recording and hand-eye calibration
├── bindings/python/        # Python client DeviceClient
├── descriptions/robots/    # Robot descriptions: URDF, model.json, configuration templates
├── examples/               # Mock configuration, C++ integration, driver extension
├── tools/  tests/  docs/   # Helper scripts, tests, interface reference, and development guide
```

**Code reading path** (the code one action passes through, top to bottom):

1. `capabilities/motion/cli/device_cli.cpp`: entry points for the `manipulation-device` subcommands.
2. `runtime/device_plan.cpp`: `LoadDevicePlan()` parses the YAML, and `DeviceRegistry` creates a driver according to `device.driver`.
3. `core/device.cpp`, `core/arm.cpp`: `DeviceSession` and `ArmSession` execute actions and verify arrival.
4. `drivers/`: drivers for each model, for example:
   - Nero: calls the vendor SDK through `drivers/common/agx_session/agx_worker.py`;
   - SO101: reads and writes servo registers through the `motor` component via `drivers/common/so101_session/`.
5. Python path: `DeviceClient` in `bindings/python/spacemit_manipulation/client.py` starts `manipulation-device serve`, which `capabilities/motion/cli/device_service.cpp` converts into session calls.

- **Platform**: Linux development machine or SpacemiT K3; the mock does not need hardware.

## 3. Examples

Run the following commands in the `~/spacemit_robot/components/control/manipulation` directory.

The steps for each real-hardware example are the same: prepare, generate configuration, read state, move. Device differences exist only in the preparation stage; commands after configuration generation are common to all devices.

Real-hardware configuration is stored in the site directory `SITE` (default `~/.local/share/spacemit-manipulation/site/`), with one subdirectory per device holding that device's configuration, poses, and calibration files:

```text
SITE/
├── nero/device.yaml
├── so101/device.yaml
├── so101/so101_calibration.json
├── so101/so101_gripper_calibration.json
└── device.yaml -> nero/device.yaml      # Current device
```

- `manipulation configure MODEL` generates `MODEL/device.yaml` and sets it as the current device;
- Other `manipulation` commands control the current device by default;
- `manipulation use` lists configured devices, and `manipulation use so101` switches the current device.

### 3.1 Example 1: Mock Joint Task

The mock simulates a two-joint arm and a six-channel end effector without connecting hardware:

```bash
manipulation-device validate examples/mock_device.yaml
manipulation-device inspect examples/mock_device.yaml
manipulation-device run examples/mock_device.yaml
```

- `validate` outputs `valid`;
- `inspect` outputs a state JSON in which `joints_rad` is `[0, 0]` and `fault` is `false`;
- `run` executes the joint targets and effector actions in the configuration's `steps` in order, and finally outputs `{"status":"succeeded","physical_grip_verified":false}`.

### 3.2 Example 2: Python Mock Control

```bash
python3 - <<'PY'
from spacemit_manipulation import DeviceClient

with DeviceClient("manipulation-device", "examples/mock_device.yaml") as device:
    print(device.state()["joints_rad"])                      # [0, 0]
    device.move_arm([0.2, -0.2], speed_scale=0.05)            # Joint targets in rad
    device.move_effector([0.5] * 6, duration_s=0.5)           # Effector channels: 0 closed, 1 open
    device.move_arm_path([[0.1, 0.1], [0.2, -0.1]], speed_scale=0.05,
                         max_velocity_rad_s=0.2, max_acceleration_rad_s2=0.5)
    start = device.state()["joints_rad"]                     # Timed trajectory: return to zero within 0.5 s
    times = [i / 10 for i in range(6)]
    device.move_arm_trajectory(times, [[q * (1 - t / 0.5) for q in start] for t in times])
    print(device.state()["joints_rad"])                      # [0, 0]
PY
```

Each action returns a result with `status` set to `succeeded` on success, and raises `DeviceCommandError` on failure.

- **Joint point targets**: each motion segment stops at its target point.
- **Continuous paths**: intermediate points are traversed without stopping; the arm stops only at the last point.
- **Timed trajectories**: the application specifies the position at each instant, which suits rhythmic motions such as shaking.

### 3.3 Example 3: Nero Arm with Revo2 Dexterous Hand

**Safety requirements**: an operator must be present, the emergency stop must be within reach, and no people or obstacles may be inside the workspace. Nero collapses when disabled or powered off; do not use disabling or power removal in place of a software stop.

**Step 1: Prepare.** Exit other control programs such as the vendor web interface and teleoperation, then bring up the CAN interface:

```bash
sudo ip link set can0 up type can bitrate 1000000
```

Nero is calibrated at the factory and needs no other preparation.

**Step 2: Generate configuration.**

```bash
manipulation configure nero --variant revo2_right    # Omit --variant revo2_right for the arm alone
manipulation validate
```

- `configure` generates `SITE/nero/device.yaml` from the model template and sets Nero as the current device.
- An existing configuration is not overwritten; to change it, move `SITE/nero/device.yaml` away first.
- If the CAN interface is not `can0`, add `--set channel=<interface name>`.

Key fields:

```yaml
device:
    driver: agx_nero_revo2          # Driver registration name
    model: nero                     # Model description used for kinematics and calibration
    arm:
        resource_id: agx_can0       # Physical resource held exclusively by the device
        tolerance_rad: 0.002        # Arrival tolerance
        timeout_s: 10               # Per-action deadline, not the motion duration
        joints:                     # Joint order and limits in rad
            - {name: joint1, minimum_rad: -2.705261, maximum_rad: 2.705261}
            # joint2–joint7 omitted
    options: {channel: can0, ...}   # Driver connection parameters, defined by the driver
steps: []                           # Sequential actions; an empty list means no motion
```

**Step 3: Read state.** Enable the arm and enter position mode according to the vendor procedure; the component does not enable it automatically:

```bash
manipulation inspect
manipulation teach start_pose.json
```

- `inspect`: reads state only. Confirm that `enabled` and `position_mode` are `true`, `fault` is `false`, and the seven joint angles match the actual pose.
- `teach`: saves the current stationary pose to `SITE/nero/start_pose.json`.

**Step 4: Move.**

```bash
manipulation joint-step joint1 0.01 --speed 0.01     # Rotate joint 1 by 0.01 rad
manipulation hand-move 1 1 1 1 1 1                   # Fully open the dexterous hand
manipulation hand-move 1 1 0.7 1 1 1 --duration 1    # Bend the index finger to 0.7
manipulation hand-move 1 1 1 1 1 1                   # Return to fully open
```

- `joint-step` returns `succeeded` when three consecutive fresh feedback samples are within tolerance and the arm is stationary. On failure, check state with `inspect` first rather than retrying directly.
- `hand-move` takes positions in the order `thumb_tip`, `thumb_base`, `index_finger`, `middle_finger`, `ring_finger`, `pinky_finger`, where `0` is closed and `1` is open; `--duration` defaults to 2 s with a maximum of 2.55 s.
- Revo2 connects through the Nero end-effector port and has no position feedback: the result is `unverified`, meaning the command was sent and the execution duration elapsed, but arrival was not measured.
- The starting position is unknown, so even a small target value can produce large motion. Before executing, confirm that no people or objects are near the fingers.

**Step 5 (optional): YAML sequential task.** Copy the configuration in the Nero site directory:

```bash
cd ~/.local/share/spacemit-manipulation/site/nero
cp device.yaml motion.yaml
```

Edit `motion.yaml` and replace `steps: []` with targets based on the measured pose:

```yaml
steps:
    - capability: joint_point
      target_rad: [J1, J2, J3, J4, J5, J6, J7]   # Change only one joint slightly; keep the measured values for the rest
      speed_scale: 0.01
    - capability: effector_position
      positions: [1, 1, 0.7, 1, 1, 1]
      duration_s: 1.0
```

```bash
manipulation-device validate motion.yaml
manipulation-device run motion.yaml
```

`run` executes `steps` in order and stops at the first failure. Exit codes: `0` success, `1` failure or interruption, `2` configuration or connection error, `3` completed but included an effector action without feedback (such as the dexterous-hand step above).

### 3.4 Example 4: SO101 Arm with Gripper

- **SO101 arm**: STS3215 servos with IDs 1–5, powered according to rated specifications;
- **Stock gripper**: STS3215 servo with ID 6, sharing the arm's serial bus;
- **USB serial board**: 1 Mbps, and the current account must belong to the `dialout` group.

**Step 1: Prepare.** Exit other serial programs such as LeRobot. The following uses `/dev/ttyACM0` as an example:

```bash
sudo usermod -aG dialout "$(id -un)"     # First use; log in again after running
ls -l /dev/serial/by-id/
```

SO101 uses general-purpose servos and must be calibrated before first use. If `so101_calibration.json` and `so101_gripper_calibration.json` for this arm already exist, place them in `SITE/so101/` to skip calibration. After a new assembly or reassembly, support the arm, remove any object from the gripper, and release torque before running:

```bash
so101-calibrate --port /dev/ttyACM0 status    # Read servo status (read-only)
so101-calibrate --port /dev/ttyACM0 all       # Complete all calibration following the prompts
```

`all` runs `configure`, `center`, `capture`, and `limits` from the table below in sequence, with the operator following the prompts:

1. Place the arm in the center pose and complete center calibration.
2. As with LeRobot, slowly rotate the first four joints through their full range to both ends one at a time. The screen updates each joint's `MIN`, `POS` (current position), and `MAX` in real time; press Enter once after all joints have been moved. `wrist_roll` can rotate continuously and does not need to be captured.
3. Move the gripper to the open and closed positions respectively.

To redo a single step (for example, to recapture only the range of motion), run the corresponding subcommand alone:

| Subcommand | Purpose |
| --- | --- |
| `status` | Read-only; one line per servo with model, torque, offset, limits, PID, protection parameters, position, load, voltage, and temperature |
| `configure` | Writes recommended parameters: P/D/I 16/0/0, return delay 0, position mode; for the gripper it also writes maximum torque 500, protection current 250 mA, and overload torque 25 |
| `center` | Center calibration: places each joint at the middle of its range (model zero), sets the encoder center to 2047, and resets servo limits to 0–4095 |
| `capture` | Range capture: displays each joint's `MIN`/`POS`/`MAX` in real time, ends on Enter, and the range must include the center; for the gripper it reads the open and closed positions; read-only and does not overwrite existing files |
| `limits` | Writes the captured range into the servo position limits |

- Calibration files are saved in `SITE/so101/` with the same filenames as the SO101 configuration template, and `configure` references them automatically.
- The tool never enables torque; except for `status`, it refuses to run when any servo has torque. Writes only change registers that differ from the current value and are read back for confirmation.
- After `center`, existing calibration files no longer match and must be moved away before running `capture` again.
- `--part arm|gripper` processes only the arm or the gripper.

**Step 2: Generate configuration.**

```bash
manipulation configure so101 --variant gripper --set port=/dev/ttyACM0    # Omit --variant gripper for the arm alone
manipulation validate
```

The configuration is saved to `SITE/so101/device.yaml` and SO101 is set as the current device. The configuration references the calibration files generated in the previous step; if those files are missing, `configure` reports an error and does not generate a configuration.

**Step 3: Read state.**

```bash
manipulation inspect
manipulation monitor
```

- `monitor` prints joint angles in degrees, gripper position, and load five times per second; end it with Ctrl+C. It is read-only, so you can release torque and move the arm by hand to observe the readings.
- With the arm in the center pose, each joint should read close to 0°.

**Step 4: Move.** Run these with an operator present and the workspace clear:

```bash
manipulation enable && manipulation hand-enable
manipulation joint-step shoulder_pan 0.05 --speed 0.2
manipulation hand-move 1.0                          # Gripper fully open; 0 is closed
manipulation hand-grasp                             # Close and report whether an object is held
manipulation pose                                   # Current end-effector pose
manipulation pose-move 0.20 0.00 0.15 --speed 0.2   # Move the end effector to base-frame coordinates (m)
manipulation line-move 0.20 0.05 0.15 --speed 0.2   # Move the end effector along a straight line
```

- **Enable**: requires every joint to be within its calibrated range; a folded pose can also be enabled directly. Errors list the current position and allowed range for each out-of-range joint.
- **Speed**: `--speed 1` corresponds to the driver option `max_velocity_rad_s` (default 1 rad/s). If the estimated duration of `pose-move` exceeds `timeout_s` (default 10 s), the motion is rejected before it starts.
- **Grasp determination**: `hand-grasp` decides whether an object is held based on the gripper's stopping position and load.
  - Stopped by an obstruction during closing with load at or above `grip_load_threshold` (default 100, i.e. 10% of rated output): the result is `effector_grasp_holding` and `physical_grip_verified` is `true`;
  - Fully closed: the result is `effector_position_reached`, meaning no object is held;
  - Stopped by an obstruction but with insufficient load: times out as a failure.

  Load-based determination is not a force measurement; observe the first grasp of a new object.
- **Inverse kinematics**: SO101 has only five joints, so by default only position is solved; add `--rpy R P Y` to solve orientation as well. The arm does not move if the solver does not converge; only joint limits are checked, not collisions.
- **Linear motion**: waypoints are interpolated every 5 mm and solved point by point. If any waypoint is unreachable or a joint jumps, the entire line is rejected before motion. SO101 does not support continuous paths, so lines are sent point by point.
- **Stopping and teaching**:
  - `hold` / `hand-hold`: hold the current position without releasing a held object;
  - `disable` / `hand-disable`: release torque; support the arm before running;
  - Re-running `enable`: targets the current position and does not jump back to the old target.

## 4. Application Development

### Choosing an Interface

- Fixed sequential joint targets: YAML `steps` with `manipulation-device run`;
- Targets generated dynamically from perception: the Python `DeviceClient` or C++ `DeviceSession`;
- End-effector pose targets and linear motion: solve IK with Python `spacemit_manipulation.urdf_ik`, then pass the result to `DeviceClient`;
- High-rate target updates such as teleoperation or visual servoing: target following with `follow_arm()` and `follow_effector()`.

### Python Interface

```python
DeviceClient(executable, plan, *, allow_motion=True, allow_enable=False, allow_disable=False,
             allow_effector_enable=False, allow_effector_disable=False)
```

`DeviceClient` starts the local control process and holds the device exclusively for its lifetime. `allow_motion=False` opens the device read-only; enabling and disabling require explicit authorization.

| Method | Purpose |
| --- | --- |
| `state()`, `diagnose()`, `capabilities()` | Read state, diagnose the device, query driver capabilities |
| `enable_arm()` / `disable_arm()`, `enable_effector()` / `disable_effector()` | Change enable state |
| `hold_arm()`, `hold_effector()` | Hold the current position without releasing torque |
| `jog_arm(joint_index, delta_rad, speed_scale)` | Relative single-joint point target |
| `move_arm(target_rad, speed_scale, tolerance_rad=0, wait_for_arrival=True)` | Joint point target |
| `follow_arm(target_rad, speed_scale)` | Target following: returns once the target is sent and can replace the target mid-motion |
| `move_arm_path(path_rad, speed_scale, max_velocity_rad_s, max_acceleration_rad_s2)` | Continuous path, at most 128 points |
| `move_arm_trajectory(times_s, positions_rad, command_rate_hz=100, effector_schedule=())` | Timed trajectory, optionally sending effector actions at scheduled times |
| `move_effector(positions, duration_s=0.5, allow_unverified=False)` | Move effector channels to the given positions (`0` closed, `1` open) |
| `follow_effector(positions, duration_s=0.1, allow_unverified=False)` | Effector target following |

All methods accept `timeout` (default 10 s) and `is_cancelled` (cancels when the callback returns `True`). Completion conditions:

| Usage | Returns when | Result |
| --- | --- | --- |
| Default | Three consecutive fresh feedback samples within tolerance and stationary | `succeeded` |
| `wait_for_arrival=False` | Point targets: two samples within tolerance; trajectories: the last point has been sent | `succeeded`, and the next command may start during the final settling |
| Effector without position feedback, or with `effector_schedule` | The command has been sent and the execution duration has elapsed | `unverified`; requires `allow_unverified=True` |
| Effector with grasp determination stopped on an object | Three consecutive samples indicate a grasp | `succeeded` with `physical_grip_verified=true` |
| `follow_arm`, `follow_effector` | The target has been sent; arrival is not awaited | `succeeded`; `unverified` for effectors without feedback |

On failure, `DeviceCommandError` is raised: the `result` field contains `status` and the reason; `rejected` being `true` means the request was refused before being written to the device, and `latched` being `true` means the session is latched and must be reconnected. See `docs/reference.md` in the component source for complete parameters.

### Target Following

For teleoperation, visual servoing, or other cases that need continuously updated targets, use target following instead of point-target motion:

```python
with DeviceClient("manipulation-device", plan) as device:
    for target in targets:                    # Produced by the application at its own rate
        device.follow_arm(target, speed_scale=0.5)
        state = device.state()                # Read the actual position and effector grasp determination
    device.hold_arm()                         # Finish: hold the current position
```

The first target requires the arm to be stationary; later targets may replace a target that is still being executed. Every target still checks joint limits, enable state, and faults. To confirm arrival at the final target, call `move_arm()` last. The update rate is limited by the device round-trip time.

### Kinematics

```python
import json, os
from pathlib import Path
from spacemit_manipulation import urdf_ik
from spacemit_manipulation.urdf_fk import UrdfKinematics

root = Path(os.environ["PREFIX"]) / "share/manipulation/descriptions/robots/so101"
config = json.loads((root / "model.json").read_text())
model = UrdfKinematics(root / config["urdf"], config["base"], config["tip"], config["joints"])
result = urdf_ik.solve(model, urdf_ik.pose([0.2, 0.0, 0.15]), seed_rad=[0.0] * 5)
if result["converged"]:
    print(result["joints_rad"])          # Pass to DeviceClient.move_arm
```

- `solve()` uses damped least squares with convergence thresholds of 0.5 mm / 0.01 rad. With `orientation_weight` at 0 only position is solved; at 1 orientation is solved as well.
- `line()` returns linear waypoints and `forward()` returns the end-effector pose.
- When tracking end-effector pose targets, use the previous solution as `seed_rad`, then pass the result to `follow_arm()`.
- A result with `converged` set to `false` must not be used as a motion target.

### Reference Implementation: Dice Game

### Integrating a New Device

Devices already supported by a driver only need a new configuration template. New hardware requires a new driver:

1. Following `examples/bench_driver/`, implement the `Arm` interface; implement `EndEffector` as well if the device has an end effector.
2. Register the driver through `DeviceRegistry` and add it to the build with `MANIPULATION_EXTRA_DRIVER_DIRS`.
3. Place the URDF, `model.json`, and configuration template in `descriptions/robots/<model>/`.

Drivers must declare capabilities truthfully: changing configuration cannot give a device capabilities it does not support, such as paths or position feedback. See `docs/development.md` in the component source for driver conventions.

### Hand-Eye Calibration

Eye-to-hand: the camera is fixed and the calibration board is mounted on the flange. The workflow is:

`hand-eye collect` (capture) → `solve` (solve and check quality) → `promote` (confirm) → `export` (export `T_base_camera`)

- The capture tool does not move the arm; poses must be set according to the device procedure before sampling.
- The model description (`device.model`) must match the actual hardware.

## 5. Debugging Guide

Troubleshoot in the order **environment → configuration → feedback → motion**, and do not send real-hardware targets until the previous step is confirmed:

| Check | Command | Focus |
| --- | --- | --- |
| Environment | `manipulation check --profile control` | Installation paths and runtime dependencies |
| Configuration | `manipulation validate`, `manipulation-device describe PLAN` | Driver, joint order, limits |
| Feedback | `manipulation inspect`, `manipulation monitor` | Actual position, enable state, faults |
| Motion | `manipulation joint-step` with a small step | Arrival and stopping state |

Handle failures according to the result:

- `cancelled`: stopping has been confirmed and you may continue;
- `timed_out` / `fault`: stopping has been confirmed and the session is latched; check the target, feedback, and device faults, then reconnect;
- `stop_unknown`: stopping cannot be confirmed; follow on-site safety procedures and do not send further targets.

After the session is latched, reconnecting only reads the actual state; it does not replay actions or automatically enable or home the device. A software stop is not a substitute for the hardware emergency stop.

### Command Reference

Device commands in `manipulation` control the current device by default, and a single command can use another configuration with `--plan FILE`. The site directory `SITE` defaults to `~/.local/share/spacemit-manipulation/site/`; to use another directory, place `--site DIR` before the subcommand.

| Command | Purpose | Motion |
| --- | --- | --- |
| `manipulation check` / `validate` / `capabilities` | Check dependencies / validate configuration / query capabilities | No |
| `manipulation configure MODEL [--variant V] [--set K=V]` | Generate `SITE/MODEL/device.yaml` from the model template and set it as the current device | No |
| `manipulation use [NAME]` | Switch the current device; list configured devices when `NAME` is omitted | No |
| `manipulation inspect` / `monitor` | Read state once / print state continuously | No |
| `manipulation teach FILE` / `fk FILE` / `pose` | Record a pose / forward kinematics of a pose / current end-effector pose | No |
| `manipulation ik X Y Z` | Solve inverse kinematics | No |
| `manipulation enable` / `disable`, `hand-enable` / `hand-disable` | Enable / release torque | Yes |
| `manipulation hold` / `hand-hold` | Hold the current position | Yes |
| `manipulation joint-step` / `joint-move` | Single-joint relative / all-joint absolute point targets | Yes |
| `manipulation hand-move` / `hand-step` / `hand-grasp` | Absolute effector positions / small steps / grasp | Yes |
| `manipulation pose-move` / `line-move` | Move the end effector to a pose / along a straight line | Yes |
| `manipulation arm-check` | Move joint 1 by 0.01 rad and back, checking cancellation and reconnection | Yes |
| `manipulation-device run PLAN` | Execute a YAML sequential task | Yes |
| `so101-calibrate all` | Full SO101 calibration; `status`, `configure`, `center`, `capture`, and `limits` can also be run individually | No |
| `hand-eye collect` / `solve` / `promote` / `export` | Hand-eye calibration | No |

See `docs/reference.md` in the component source for complete parameters.

## 6. Troubleshooting

| Problem | Resolution |
| --- | --- |
| Command or Python module not found | Enter `~/spacemit_robot` and re-run `source build/envsetup.sh` |
| Device reported as in use | Exit other control programs; do not delete lock files or modify resource identifiers to bypass this |
| Nero connection failure | Check `ip -details link show can0` (should be `UP` at 1 Mbps), the power supply, and the vendor SDK |
| `run` returns `idle` | `steps` is empty; configuration templates contain no actions by default |
| `ik` does not converge or `line-move` is rejected | The target is outside the workspace or joint limits; for SO101, remove `--rpy`; split the line into segments when it crosses a singularity |
| `pose-move` reports a duration exceeding `timeout_s` | Increase `--speed` or move in segments |
| Multiple arm types on one host | Run `configure` for each, then switch the current device with `manipulation use NAME`, or add `--plan FILE` to a single command |
| Multiple arms of the same model | Use one site directory per arm: pass the same `--site DIR` before the subcommands of both `manipulation` and `so101-calibrate` |
| SO101 gripper refuses to enable | Release torque, then run `so101-calibrate configure` |
| SO101 reports an offset that does not match the calibration file | The offset has changed (for example after `center`); move the old calibration file away and run `so101-calibrate capture` again |
| Calibration solver not found | Install OpenCV and rebuild with `-DMANIPULATION_ENABLE_CALIBRATION=ON` |
