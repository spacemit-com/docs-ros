# Localization and Navigation · SpacemiT VSLAM

## 1. Module Overview

`spacemit-vslam` provides stereo visual localization, visual-inertial localization, and 3D reconstruction for robots. It lives in the Robot SDK at `middleware/ros2/slam/spacemit-vslam`. The module keeps camera input, VSLAM, and TSDF/ESDF mapping in one repository, and uses ROS 2 packages for data publishing, scheduling, and desktop display.

Key features:

- Stereo VO/VIO: publishes the pose at each image timestamp, the trajectory, features, and the tracking state.
- LAS2 stereo depth: reuses the SDK's `stereo_matching` component to publish depth and an aligned RGB descriptor.
- TSDF/ESDF: fuses depth and pose into a colored 3D surface and gravity-aligned ESDF slices.
- Desktop window: shows the live image, colorized depth, TSDF, and ESDF in a normal or full-screen window.
- K3 data path: images and depth stay in DMA-BUF; ROS 2 / DDS carries only descriptors and metadata.

The example in this guide runs stereo VIO with real-time TSDF/ESDF reconstruction. A healthy VIO track does not mean loop closure or global relocalization has run; the entry point used here leaves loop closure and PGO off by default.

```text
Stereo camera (image with embedded exposure timestamps and IMU)
  │
  ▼
camera_io ── left/right descriptors / CameraInfo / IMU
  ├── vio ───────────── pose / trajectory / features / tracking state
  └── las2 ──────────── depth and aligned RGB descriptor
           │              │
           └──────┬───────┘
                  ▼
               esdf_drm ── TSDF / ESDF / composited frame
                  │
                  ▼
           esdf_desktop_viewer ── desktop window
```

Directories and their responsibilities:

| Path | Responsibility |
| --- | --- |
| `modules/camera/` | Native camera, metadata, calibration, and time-alignment utilities |
| `modules/vslam/` | CPU/RVV visual localization SDK |
| `modules/mapping/` | TSDF/ESDF, map, and GLES rendering SDK |
| `src/camera_io/` | ROS camera integration, image and IMU publishing, and recording |
| `src/vio/` | ROS wrapper for the VSLAM SDK |
| `src/las2/` | ROS wrapper for the SDK LAS2 depth inference |
| `src/esdf_drm/` | Depth/pose pairing, asynchronous reconstruction, and desktop display |
| `src/common/` | Shared messages and readiness interface |
| `src/bringup/` | Cross-package launch and run scripts |
| `dependencies/` | SDK dependency paths and source manifest; does not contain dependency implementation sources |

MPP, LAS2, and the IMU DDS interface reuse existing SDK directories: `components/multimedia/mpp`, `components/perception/stereo_matching`, and `middleware/ros2/peripherals/imu`.

## 2. Environment Setup

### 2.1 Prerequisites

For SDK checkout, software sources, and the base build environment, see [2.3 Building and Compilation](../../02-快速入门/2.3-构建编译.md). On a first deployment, prepare the environment before building this module. When a build fails, keep the log and identify the missing component and its version first. Do not upgrade drivers, mix packages from different distributions, or change global environment variables as the default response.

The SDK workspace must already contain this module's source and the matching LAS2 ExternalStereo backend. An older SDK that only exposes the tensor inference interface cannot build this example.

This module requires:

| Item | Requirement |
| --- | --- |
| Board | A K3 board with MPP, V2D, DMA-BUF, and GLES/OpenCL support |
| System | A Bianbu image matched to the board drivers; this example uses Bianbu 4.0.1 |
| ROS | ROS 2 Humble as shipped with the image |
| Build dependencies | The CMake/C++, Eigen, YAML, Boost, LMDB, OpenCV, multimedia, Fast DDS, and graphics development libraries declared by the SDK |
| Camera | A stereo USB camera whose current driver supports embedded hardware timestamps and IMU; a plain UVC camera cannot substitute for that metadata protocol |
| Desktop | A logged-in graphical desktop with X11 or Xwayland, and a GPU EGL implementation that supports DMA-BUF import |
| LAS2 artifacts | ORT/EP, development headers, and the FP16 model matched to the ExternalStereo backend |
| Calibration | A Kalibr stereo and camera-IMU YAML for the physical camera in use, plus an IMU noise YAML |

The EGL/GLES development libraries only provide the generic interfaces; they do not replace the PowerVR driver. The K3/Bianbu graphics stack should include `img-gpu-powervr`, `libegl-pvr0`, `libgbm1-pvr`, `libgl1-pvr-dri`, `libglapi-pvr`, and `pvr-vulkan-drivers`. This project's `src/esdf_drm/package.xml` already declares these target-machine dependencies. When using the software-setup skill, check that package directly, or check each package individually. Checking only the SDK dependency closure of `src/bringup` does not recurse into its ROS runtime dependencies, and the project-root `mm` does not automatically walk the system dependencies of subpackages. A board that only compiles the source without the matching driver can still fall back to software rendering; dependency declarations do not replace board firmware and driver integration.

The K3/Bianbu 4.0.1 setup verified for this guide kept the existing `img-gpu-powervr=24.2-6603887bb22` and added the five `24.0.1-bb3` PVR split packages, which coexist with the system Mesa 26. After installing the driver for the first time, save your desktop work and log in again so the compositor and Xwayland load the new driver. For day-to-day use, leave the desktop services running. Optionally run `eglinfo -B -p x11` to check PowerVR/OpenGL ES 3; the application's actual renderer is the final authority.

For example, from the SDK root, use the existing checker to inspect the graphics packages explicitly. The following command only checks; it does not install:

```bash
source build/common.sh
AUTO_INSTALL_DEPS=no check_and_install_dependencies_for_package \
  middleware/ros2/slam/spacemit-vslam/src/esdf_drm none
```

Resolve any missing items through the board-side software preparation flow of the software-setup skill before continuing with the build below.

The SDK deployment package provides the ORT/EP artifacts. Download the LAS2 model separately from the archive site rather than placing it in this project's `dependencies/` directory. Save it in your user directory, and verify that it matches the ExternalStereo version identified by the SHA256 checksum below before using it. Running `source build/envsetup.sh` sets the SDK root in `SROBOTIS_ROOT`:

```bash
export ARTIFACT_ROOT="$HOME/spacemit-vslam-artifacts"
mkdir -p "$ARTIFACT_ROOT/model"
wget -O "$ARTIFACT_ROOT/model/LAS2_M_288x384.fp16.onnx" \
  https://archive.spacemit.com/spacemit-ai/model_zoo/vision/stereo_depth/LAS2_M_288x384.fp16.onnx && \
echo "aa4f22f0f2433dc317ae3fa028549b9e228200c117d95121e19cfa0f1615145a  $ARTIFACT_ROOT/model/LAS2_M_288x384.fp16.onnx" | sha256sum -c -
```

Continue the build only after the checksum prints `OK`. If the download fails or the checksum does not match, stop, delete `$ARTIFACT_ROOT/model/LAS2_M_288x384.fp16.onnx`, confirm the archive site provides the ExternalStereo version above, then download and verify it again.

Example artifact layout:

```text
spacemit-vslam-artifacts/
  onnxruntime/
    LICENSE                  # license file of the matching artifacts; required at build install time
    include/                 # matching ORT/EP development headers
    lib/                     # matching ORT, SpacemiT EP, and TCM runtime libraries
  model/
    LAS2_M_288x384.fp16.onnx
```

Unpack the ORT artifacts completely and keep the relative SONAME/dlopen symlinks under `lib/`. Do not copy only two directories or a single library file. The build fails explicitly when `LICENSE` is missing.

The backend and the model must match. The SHA256 of the matching `LAS2_M_288x384.fp16.onnx` is:

```text
aa4f22f0f2433dc317ae3fa028549b9e228200c117d95121e19cfa0f1615145a
```

The same file name does not mean the same model. The model used by ExternalStereo and the original tensor SDK model are managed separately. See `components/perception/stereo_matching/RUNTIME_CONTRACT.json` in the SDK for the runtime library and interface requirements.

### 2.2 Build

On the K3 board, open a new terminal without running `lunch`, then use the SDK's single-module build command. The current SDK does not support the `-b` option for `m`. If there is no dedicated target for this module, run `mm` from the project directory; you do not need to add a target or modify the SDK build scripts.

```bash
cd "$HOME/spacemit_robot"
source build/envsetup.sh
export ARTIFACT_ROOT="$HOME/spacemit-vslam-artifacts"

cd "$SROBOTIS_ROOT/middleware/ros2/slam/spacemit-vslam"
mm -j4 -- \
  -DONNXRUNTIME_ROOT="$ARTIFACT_ROOT/onnxruntime" \
  -DSTEREO_MATCHING_EXTERNAL_INPUT_MODEL="$ARTIFACT_ROOT/model/LAS2_M_288x384.fp16.onnx"
```

The command above installs to the default `output/staging` prefix. If you use an isolated output directory, explicitly pass `-DSPACEMIT_SDK_PREFIX="$PREFIX"` and `-DMPP_BUILD_DIR="$PREFIX"` in the same SDK environment. This ensures that dependent components find MPP and other SDK dependencies in that build's installation prefix.

`mm` uses the project's existing `build.sh` interface in the SDK to build its native modules, shared dependencies, and six ROS packages. The project manages the CMake and colcon build steps internally; you do not need to modify the SDK's `build/`, the original IMU package, or `target/`.

Artifacts:

- The default install prefix is `$SROBOTIS_ROOT/output/staging`.
- Node executables are under `lib/<ROS package name>/`, and shared libraries are under `lib/`.
- ROS configuration, launch files, and resources are under `share/<ROS package name>/`.
- The matching ExternalStereo model is installed to `share/stereo_matching/external_input/model/`.
- Deployment artifacts such as ORT/EP are installed to the prefix at the paths explicitly provided, not into the project's dependency source directory.
- Stop high-load programs such as the camera, inference, and mapping while compiling.

In a new terminal, load the generated SDK runtime environment:

```bash
cd "$HOME/spacemit_robot"
source build/envsetup.sh
sros2_setup
```

`m` builds the whole SDK from its root, and `mm` builds the current component. This guide does not require building every other robot solution from the SDK root.

## 3. Example Usage

### 3.1 Prepare the camera configuration and calibration

Keep the on-robot configuration in a runtime directory the user can read and write, instead of editing the installed shared configuration directly:

```bash
cd "$HOME/spacemit_robot"
source build/envsetup.sh
export CONFIG_ROOT="$HOME/spacemit-vslam-config"
mkdir -p "$CONFIG_ROOT"
cp "$SROBOTIS_ROOT/middleware/ros2/slam/spacemit-vslam/src/camera_io/config/usb_stereo_4000x1200.json" \
  "$CONFIG_ROOT/camera.json"
```

Save the current camera's Kalibr calibration as `$CONFIG_ROOT/camchain-imucam.yaml` and its IMU noise calibration as `$CONFIG_ROOT/imu.yaml`. Cameras with the same model number do not necessarily share the same calibration. If you replace the camera or lens, change the left/right arrangement, or change the mounting extrinsics, use a calibration that matches the new setup.

First confirm the actual device and the capture modes it supports:

```bash
ls -l /dev/v4l/by-id/
v4l2-ctl --list-devices
v4l2-ctl -d /dev/videoX --list-formats-ext
```

Replace `/dev/videoX` with the actual capture device. Do not treat a hardware decoder device or a UVC metadata device as the image capture device. Prefer the stable device path `/dev/v4l/by-id/...-video-index0` in the JSON.

Edit `camera.json` and check these fields in particular:

| Field | Configuration requirement |
| --- | --- |
| `camera.device` | The actual capture device; prefer the stable by-id path |
| `camera.width/height/fps` | Must match a capture mode the driver actually supports; the stereo example here is MJPEG 4000×1200@30 |
| `timestamp.source` | Must match the calibration and the camera protocol; the example uses `embedded_exposure_midpoint` |
| `calibration.file` | Absolute path of the Kalibr YAML for the current camera |
| `streams.left/right.crop` | Must match the physical left and right cameras and the calibration order |
| `streams.left/right.output` | 640×400 for this example, matching the launch parameters |
| `metadata.region` | Must match the embedded timestamp/IMU data region of this camera |
| `imu.samples_per_frame` | Must match the actual camera protocol; the current example uses 10 samples per frame |
| `buffers.decoder_input_pool.enabled` | Set to `false` for the current MPP API6 example, which uses the standard compressed input path |

In this camera's packed format, the left crop is `(2080, 0, 1920, 1200)` and the right crop is `(160, 0, 1920, 1200)`. These crops reflect the physical arrangement of this model; do not swap them based on their positions in the image. For other formats, update the camera configuration, calibration, and parsing support together.

For the 4000×1200@30 camera used here, after confirming the device and placing both calibration files, apply the following configuration update. Enter the actual image capture device path found by the previous command, preferring the by-id path:

```bash
read -r -p 'Image capture device path: ' CAMERA_DEVICE
export CAMERA_DEVICE
python3 - <<'PYCONFIG'
import json
import os
from pathlib import Path

config_root = Path(os.environ["CONFIG_ROOT"])
device = Path(os.environ["CAMERA_DEVICE"])
calibration = config_root / "camchain-imucam.yaml"
imu_calibration = config_root / "imu.yaml"
if not device.is_char_device():
    raise SystemExit(f"Image capture device does not exist or is not a character device: {device}")
for path in (calibration, imu_calibration):
    if not path.is_file():
        raise SystemExit(f"Prepare the calibration file for the current camera first: {path}")
path = config_root / "camera.json"
config = json.loads(path.read_text())
config["camera"]["device"] = str(device)
config["camera"]["fps"] = 30
config["calibration"]["file"] = str(calibration.resolve())
config["buffers"]["decoder_input_pool"]["enabled"] = False
path.write_text(json.dumps(config, ensure_ascii=False, indent=2) + "\n")
print(f"Updated camera configuration: {path}")
PYCONFIG
```

This snippet only updates the example configuration. It does not change calibration values or the driver. If the hardware supports a different capture mode, adjust the format, size, crops, and the matching calibration before starting.

Disabling the optional fixed compressed input pool does not disable the DMA-BUF output of images or depth. If the SDK reports that the fixed input pool extension is missing, check this option; do not remove the capability check.

### 3.2 Start the window on a normal desktop

Start the window from a terminal in an active desktop session on the board. Place the SDK, configuration, and deployment artifacts in directories accessible to that user. The window connects using the current session's `DISPLAY/XAUTHORITY`; keep the desktop services running.

Access to the camera, MPP, V2D, TCM, and DMA-BUF requires the appropriate permissions. On the image tested for this guide, the entire hardware pipeline runs with administrative privileges, while `SPACEMIT_DESKTOP_UID` identifies the logged-in desktop user. The display process uses that desktop identity only to establish the X11/Xwayland connection, then returns to the runtime identity. The backend and display process therefore exchange DMA-BUFs under the same identity. This option does not change X11 access rules, shared-memory permissions, or user groups.

Run the following commands in a **normal desktop user's** terminal. `sudo` uses the administrative authorization already configured on that system; it does not install or configure the system environment:

```bash
export CONFIG_ROOT="$HOME/spacemit-vslam-config"
cd "$HOME/spacemit_robot"
source build/envsetup.sh
desktop_uid=$(id -u)

sudo env SROBOTIS_ROOT="$SROBOTIS_ROOT" CONFIG_ROOT="$CONFIG_ROOT" \
  DISPLAY="$DISPLAY" XAUTHORITY="${XAUTHORITY:-$HOME/.Xauthority}" \
  WAYLAND_DISPLAY="${WAYLAND_DISPLAY:-}" XDG_RUNTIME_DIR="${XDG_RUNTIME_DIR:-}" \
  SPACEMIT_DESKTOP_UID="$desktop_uid" ROS_DOMAIN_ID=0 bash -c '
    set -e
    cd "$SROBOTIS_ROOT"
    source build/envsetup.sh
    sros2_setup
    exec ros2 run bringup run_vslam_desktop.sh \
      camera_config_file:="$CONFIG_ROOT/camera.json" \
      calibration_file:="$CONFIG_ROOT/camchain-imucam.yaml" \
      imu_calibration_file:="$CONFIG_ROOT/imu.yaml" \
      camera_fps:=30 image_width:=640 image_height:=400 use_imu:=true
  '
```

If the current non-administrative user already has access to all hardware resources and runs both the backend and the window, use the same `ros2 run bringup run_vslam_desktop.sh ...` command without setting `SPACEMIT_DESKTOP_UID`. Do not run the backend with administrative privileges and the window as a different user: cross-user DMA-BUF file descriptor lookup can fail with the current MPP implementation.

The camera JSON's `imu.domain_id` and the ROS node's `ROS_DOMAIN_ID` must match; this example uses 0 for both. By default it opens a 1280×720 normal window. For full screen, append `desktop_fullscreen:=true` to the end of the `ros2 run` arguments.

The window shows:

- Top left: the live left image and the colorized depth preview.
- Left side: the colored TSDF surface and the camera trajectory.
- Right side: the gravity-aligned ESDF slices.
- Status area: the VO/VIO state, the localization, depth, and fusion frame rates, and the GPU time.

After startup, hold the camera steady first, then translate it slowly and rotate it slightly in a textured, evenly lit scene. The state may show `WAIT` and then `VO - IMU INIT` before entering `VIO` once inertial initialization finishes. A preview that is already showing images is not evidence that VIO initialization is complete.

By default the camera waits for `/las2/ready` before it starts publishing, so a short wait during the first model initialization is part of startup. To exit, press `Ctrl+C` in the startup terminal and let the nodes finish releasing their buffers.

### 3.3 Check the output

In another terminal with the same SDK overlay loaded, run:

```bash
ros2 node list
ros2 topic hz /camera/left/frame_desc
ros2 topic hz /las2/depth_desc
ros2 topic hz /vio/pose/image
ros2 topic echo /vio/tracking_mode --qos-reliability best_effort --once
```

The VIO state and metadata topics use sensor-data QoS. Subscribers should use a compatible best-effort, volatile configuration. `ros2 topic hz` reports an observed receive rate; the rate received by a Python subscriber listening to multiple topics should not be taken as algorithm throughput or a lossless IMU publishing rate.

## 4. Application Development

Main interfaces:

| Interface | Type | Description |
| --- | --- | --- |
| `/camera/left/frame_desc`, `/camera/right/frame_desc` | `mpp_msgs/msg/MppVideoFrameDesc` | Left and right NV12 DMA-BUF descriptors |
| `/camera/left/camera_info`, `/camera/right/camera_info` | `sensor_msgs/msg/CameraInfo` | Camera intrinsics corresponding to the output resolution |
| `/camera/imu/data_raw` | `sensor_msgs/msg/Imu` | Raw IMU samples with hardware timestamps |
| `/vio/pose/image` | `nav_msgs/msg/Odometry` | Pose at the image timestamp |
| `/vio/trajectory` | `nav_msgs/msg/Path` | Bounded trajectory output |
| `/vio/tracking_mode` | `std_msgs/msg/String` | States such as `WAIT`, `VO - IMU INIT`, and `VIO` |
| `/vio/features` | `common/msg/FeaturePointArray` | Features and optional diagnostic data |
| `/las2/depth_desc` | `common/msg/DmaDepthFrameDesc` | Depth, aligned RGB, and calibration metadata |
| `/esdf/render/frame_desc` | `mpp_msgs/msg/MppVideoFrameDesc` | NV12 composited frame for the desktop window |

Usage notes:

- Tokens in descriptors are not ordinary process addresses. New consumers should import them through the MPP interface and release the corresponding references on every exit path.
- Keep the frame number, exposure timestamp, size, stride, pixel format, and calibration. Pair images and poses by their source timestamps.
- Do not modify shared input buffers. Queues use bounded processing and may drop stale frames; inference or mapping must not block the camera or IMU.
- This entry point disables external high-frequency pose extrapolation by default. No output on `/vio/pose/imu` does not mean the raw IMU has stopped, and it does not mean VIO is not fusing the IMU.
- General application threads default to cores 0–7. The EP instance affinity parameters for LAS2 are configured independently; do not infer the board's physical CPU state from `nproc`.

Common parameters:

| Parameter | Description |
| --- | --- |
| `camera_config_file` | Camera JSON, covering the device, capture mode, crops, metadata, and IMU protocol configuration |
| `calibration_file` | Kalibr stereo and camera-IMU calibration |
| `imu_calibration_file` | IMU noise and random-walk calibration |
| `camera_fps` | Capture frame rate; must be a mode the hardware supports |
| `image_width/image_height` | Stereo output size; must match the camera configuration |
| `model_path` | Overrides the default ExternalStereo FP16 model path |
| `use_imu` | Selects VIO; when disabled, the corresponding entry point and calibration run VO |
| `desktop_fullscreen` | Normal window or full screen |
| `display_width/display_height` | Desktop window size |
| `las2_instance_count/las2_threads_per_instance/las2_core_affinity` | Inference instance count, thread count, and EP affinity parameters |

To list all launch parameters:

```bash
ros2 launch bringup vio_las2_esdf_launch.py --show-args
```

## 5. Debugging Guide

### 5.1 Camera calibration and time alignment

A Kalibr stereo calibration should contain at least the following:

| Item | Requirement |
| --- | --- |
| `cam0`, `cam1` | Correspond to this project's physical left and physical right cameras respectively |
| `camera_model` | `pinhole` |
| `distortion_model` | `equidistant` or `radtan`, as supported by the driver |
| `intrinsics` | `fx, fy, cx, cy` at the original monocular resolution |
| `distortion_coeffs` | The four parameters matching the distortion model |
| `resolution` | Must match the corresponding crop region; `[1920, 1200]` in this example |
| `cam1.T_cn_cnm1` | The rigid transform for the non-zero stereo baseline, keeping the Kalibr direction |
| `T_cam_imu` | Rotation and translation between the camera and the IMU; VIO needs the matching calibration |
| `cam0.timeshift_cam_imu` | The time offset from calibration, applied with the program's existing semantics |

The IMU YAML uses an `imu0` node containing `gyroscope_noise_density`, `gyroscope_random_walk`, `accelerometer_noise_density`, and `accelerometer_random_walk`, and may record `update_rate`. The actual IMU processing rate is determined by the camera capture mode and the number of samples per frame; for example, 30 FPS × 10 samples is about 300 Hz.

The image and the embedded IMU share the hardware clock. The program aligns them as `raw IMU timestamp - timeshift_cam_imu` and does not add an artificial delay to the image. Do not change the time offset arbitrarily to suppress visible jitter.

When scaling images, the program scales `fx/fy/cx/cy` to the output size. Distortion coefficients and rigid extrinsics are not scaled with resolution. Scaling the original calibration by hand before passing it to the node can apply the scaling twice.

Troubleshooting order:

1. Check the physical camera, the left and right cameras, the capture mode, and the source of the calibration.
2. Check the JSON crop regions against the Kalibr monocular original resolution.
3. Check that the JSON `calibration.file` and the launch parameter `calibration_file` use the same calibration.
4. Read the calibration source, time offset, IMU noise, and operating rate in the startup log.
5. Observe `/camera/left/camera_info`, the image and IMU timestamps, and `tracking_mode`.

```bash
ros2 topic echo /camera/left/camera_info --once
ros2 topic echo /camera/imu/data_raw --qos-reliability best_effort --once
ros2 topic echo /vio/pose/image --qos-reliability best_effort --once
```

### 5.2 Desktop window

Run the startup command in a terminal on the logged-in desktop:

```bash
printf 'DISPLAY=%s\n' "${DISPLAY:-}"
ros2 topic hz /esdf/render/frame_desc
```

The window cannot be created when `DISPLAY` is empty, X11 authorization fails, or only plain Wayland is available without Xwayland. Keep the current session's `DISPLAY/XAUTHORITY`. When running with administrative privileges, also specify the desktop UID as described in Section 3.2. Do not run `xhost +`, and do not shut down the desktop to get the window to display.

This entry point has the GPU generate composited frames in the background, which the desktop viewer then displays. The internal `headless_render=true` therefore means it does not take over the DRM scanout directly; the foreground window is created by `desktop_viewer_enabled=true`. Seeing that parameter does not mean the window is disabled.

When the window is created successfully, the log should show `Desktop EGL ready`, and the actual `renderer` should be PowerVR. A renderer of `llvmpipe` or `softpipe` indicates CPU software rendering. GLES logs or the HUD's OpenCL timing alone do not prove that the map is rendered on the GPU. By default, the window rejects known software rasterizers and prompts you to check the driver. Only for debugging, explicitly pass `desktop_allow_software_rendering:=true`.

Once frames are received and displayed, the log shows `Desktop displayed frames=...`. If the composited-frame topic has data but the window displays no frames, preserve the logs and check for DMA-BUF or token import errors. Also check that the desktop user can access the SDK installation prefix and devices.

### 5.3 Localization, depth, and load

- Stuck on `VO - IMU INIT` for a long time: first confirm the IMU is continuous and that the time alignment and calibration match, then check whether the camera gets enough translational and rotational excitation.
- Pose jumps or tracking loss: check for swapped left and right cameras, the distortion model, texture, exposure, motion blur, and monotonic timestamps.
- Pose but no depth: check the matching model and ORT, `/las2/ready`, and the depth descriptor. Do not substitute the same-named tensor model.
- Depth data but no map update: check the pose at the image timestamp, the depth timestamp, the valid depth range, and gravity initialization.
- Frame rate drop: observe the camera, VIO, LAS2, fusion, and rendering times separately. A bounded queue dropping stale frames is not a camera fault.
- Do not hide a load problem by enlarging queues, and do not compile while the high-load pipeline is running.

## 6. Common Issues

| Symptom | Possible Cause | Resolution |
| --- | --- | --- |
| `m -b` reports an unknown option | The current SDK does not support that argument | Use `mm -j4 -- -D...` in this project's directory |
| ORT/EP development headers or runtime libraries not found | The matching artifacts are incomplete or the path is wrong | Check `ONNXRUNTIME_ROOT`, keep the error, and do not mix in runtime libraries from other model packages |
| Build succeeds but model loading fails at startup | The model is missing, the ABI does not match, or the same-named tensor SDK model was used by mistake | Check the model path and SHA256, and use the ExternalStereo artifacts |
| No camera image | A decoder or metadata device was selected, the capture mode is unsupported, or the device is busy | Confirm the capture node and the formats and frame rates it actually supports using the stable by-id path |
| Fixed input pool extension reported missing | The JSON enables an optional input pool the current MPP does not support | Set `decoder_input_pool.enabled` to `false` in this example configuration |
| Calibration validation fails | The left/right cameras, crops, resolution, distortion, or IMU YAML do not match | Check the configuration as described in Section 5.1, and use the calibration for the current physical camera |
| Image present but VIO not initialized | No valid IMU data or insufficient motion excitation | Check the IMU, calibration, and timestamps, and translate the camera slowly with small rotations |
| `/vio/pose/imu` is empty | This entry point does not enable external high-frequency extrapolation by default | Check the raw IMU and the image pose; enable extrapolation later only if the application needs it |
| Desktop reports `Cannot open X11 desktop` | No valid desktop session, or the user authorization does not match | Keep the desktop environment; when running with administrative privileges, set `SPACEMIT_DESKTOP_UID` as described in Section 3.2 |
| TCM shared-memory permission error or V2D access failure | The runtime identity lacks the hardware permissions the image requires | Start with an authorized administrative identity, keep the log, and do not chmod or change user groups as a workaround |
| Window keeps reporting `NV12 DMA-BUF lookup failed` | The backend and the window run as different users, so the fd lookup is denied | Keep the same runtime identity as described in Section 3.2, and specify the desktop connection identity separately with the UID |
| Map keeps updating but no window appears | The viewer was not started, or the composited frame is not published | Use `run_vslam_desktop.sh`, and check `/esdf/render/frame_desc` and the viewer log |
| Displayed motion does not match the actual motion direction | The physical left/right cameras or the camera/IMU extrinsic direction is wrong | Recheck the calibration direction and the physical mounting; do not patch the odometry through display coordinates |
