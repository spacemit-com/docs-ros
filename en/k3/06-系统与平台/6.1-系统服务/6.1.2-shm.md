# System Services · Shared Memory

## 1. Overview

- **Key Features**: A shared-memory allocation library built on Linux DMA-HEAP. It provides cross-process zero-copy transfer capability, supports DMA-BUF file descriptor passing and cache sync operations, and works together with libdma for efficient data transfer.
- **Specifications and Features**:
  - Supports DMA-HEAP allocation, with configurable attributes such as physically contiguous and non-cached.
  - Supports cache sync operations (TO_DEVICE / FROM_DEVICE).
  - shm_transport: an fd-passing framework based on Unix domain sockets, supporting a publish/subscribe model.
  - Supports multiple memory domains: POSIX shared memory, DMA-BUF, and physical memory.
- **Directory Structure**:

  ```text
  components/system/shm/
  ├── include/
  │   ├── shm.h              # Shared-memory allocation API
  │   └── shm_transport.h    # Cross-process transport API
  ├── src/                   # Library implementation source
  ├── test/
  │   ├── shm_transport_pub_test.c  # Publisher test
  │   └── shm_transport_sub_test.c  # Subscriber test
  ├── CMakeLists.txt         # Build configuration
  └── README.md              # Module documentation
  ```

## 2. Environment Setup

### Prerequisites

- **Runtime Environment**: Linux kernel (with DMA-HEAP support), CMake ≥ 3.16, gcc/clang compiler.
- **Dependencies and External Resources**:
  - The kernel must support DMA-HEAP (the `/dev/dma_heap/*` device nodes exist).
  - No additional external dependencies — only the standard C library and pthread.
- **Environment Variables and Initialization**: If building through the SDK, first run `source build/envsetup.sh` and `lunch <target>`.
- **Hardware and Connections**: The target board must support DMA-HEAP; confirm that the `/dev/dma_heap/` directory exists.
- **Tools and Permissions**: Accessing the `/dev/dma_heap/*` device nodes requires the corresponding permissions (typically root or membership in the corresponding user group).

### Build

- **Getting the Code**: The code is located in the SDK's `components/system/shm` directory.
- **Module Compilation**:

    **Standalone build:**

    ```bash
    cd components/system/shm
    mkdir build && cd build
    cmake ..
    cmake --build .
    ```

    **Build via SDK `mm`:**

    ```bash
    source build/envsetup.sh
    lunch <target>
    cd components/system/shm
    mm clean && mm -v
    ```

- **Artifacts**:
  - User-space library: `libshm.so` or `libshm.a`
  - Test programs: `build/output/shm_transport_pub_test`, `build/output/shm_transport_sub_test`

## 3. Example Usage (From Scratch)

This section provides a step-by-step path for readers to reproduce the examples from scratch: commands are copy-ready, paths are absolute or state the working directory, and each step gives the **expected result** (terminal output snippets, exit codes, UI or log keywords).

### 3.1 Cross-Process Shared-Memory Transfer

**Prerequisites**: libshm is built; the target board is powered on and accessible via serial or SSH.

**Step 1**: Confirm the DMA-HEAP device nodes exist.

```bash
ls -l /dev/dma_heap/
```

Expected result: The available heap devices are shown, such as `system`, `cma`, etc.

**Step 2**: Start the publisher (terminal 1).

```bash
cd components/system/shm/build/output
./shm_transport_pub_test
```

Expected result: The program starts and waits for subscribers to connect, printing output similar to:

```text
[INFO] Publisher opened: /tmp/shm_trans_test.sock
[INFO] Waiting for subscribers...
```

**Step 3**: Start the subscriber (terminal 2).

```bash
cd components/system/shm/build/output
./shm_transport_sub_test test
```

Expected result: The subscriber connects successfully and begins receiving data frames, printing output similar to:

```text
[INFO] Subscriber connected to: test
[INFO] Received frame: seq=0, size=4096, timestamp=...
[INFO] Data verification passed
```

The publisher simultaneously shows:

```text
[INFO] Subscriber connected
[INFO] Publishing frame: seq=0, size=4096
```

### 3.2 Shared-Memory Allocation and Cache Sync

**Prerequisites**: See Section 2.

**Step 1**: Write test code to allocate shared memory (refer to the examples in the `test/` directory).

**Step 2**: Allocate a physically contiguous DMA buffer.

```c
struct shm_domain *domain = shm_create_domain_dmabuf("system");
struct shm_buffer buf;
shm_alloc(domain, 1024*1024, SHM_FLAG_CONTIGUOUS, &buf);
```

Expected result: Allocation succeeds; `buf.vaddr` points to usable memory, and `buf.fd` is a valid file descriptor.

**Step 3**: Perform a cache sync operation.

```c
// After the CPU writes data, sync it to the device
shm_sync_cache(domain, &buf, SHM_SYNC_TO_DEVICE);
```

Expected result: The cache flush completes, and the data is visible to the DMA device.

## 4. Application Development

- **API / Interface**:

  - Header files: `include/shm.h` (shared-memory allocation), `include/shm_transport.h` (cross-process transport)
  - Library name: `libshm.so` or `libshm.a`
  - Main APIs (shm.h):
    - `shm_create_domain_dmabuf()` — create a DMA-BUF memory domain
    - `shm_alloc()` — allocate shared memory
    - `shm_import_fd()` — import an existing fd
    - `shm_sync_cache()` — cache sync operation
    - `shm_free_buffer()` — release a buffer
    - `shm_destroy_domain()` — destroy a memory domain
  - Main APIs (shm_transport.h):
    - `shm_trans_pub_open()` — open the publisher
    - `shm_trans_pub_add_buffer()` — add a buffer to the transport pool
    - `shm_trans_pub_acquire()` — acquire a writable buffer
    - `shm_trans_pub_publish()` — publish a data frame
    - `shm_trans_sub_open()` — open the subscriber
    - `shm_trans_sub_recv()` — receive a data frame
    - `shm_trans_sub_release()` — release a data frame
- **Usage and Notes**:

  - Thread safety: A single domain/pub/sub object does not support concurrent access from multiple threads; the upper layer must add locking.
  - Permissions: Ensure the `/dev/dma_heap/*` device nodes are accessible.
  - Resource cleanup: Release in order — call `shm_free_buffer()` first, then `shm_destroy_domain()`.
  - fd lifecycle: `shm_buffer.fd` stays valid until the buffer is released and can be used for cross-process passing.
  - Cache sync: Call `shm_sync_cache()` before and after a DMA transfer to ensure data consistency.
  - Transport model: On the publisher side, call `add_buffer()` before `acquire()`; on the subscriber side, always `release()` after `recv()`.
- **Reference demos and example paths**: `components/system/shm/test/shm_transport_pub_test.c`, `shm_transport_sub_test.c`

## 5. Debugging Guide

- **Kernel log inspection**: `dmesg | grep dma_heap` shows DMA-HEAP-related logs.
- **User-space logging**: Add `printf` statements in the code or use `strace` to trace system calls.
- **Common debugging steps**:
  1. Confirm the DMA-HEAP devices exist: `ls -l /dev/dma_heap/`
  2. Check permissions: `sudo chmod 666 /dev/dma_heap/*` (for testing)
  3. Check the socket file: `ls -l /tmp/shm_trans_*.sock`
  4. Use `lsof` to check for fd leaks: `lsof -p <pid> | grep dma_heap`
  5. Trace with `strace`: `strace -e ioctl,mmap ./test_program`
- **Information collection checklist when working with hardware/kernel colleagues**:
  - Kernel version and DMA-HEAP configuration (`cat /proc/config.gz | gunzip | grep DMA_HEAP`)
  - List of available heaps (`ls /dev/dma_heap/`)
  - The dmesg log at the time of the allocation failure
  - Memory usage (`cat /proc/meminfo`)

## 6. FAQ

| Symptom | Possible Cause | Resolution |
| --- | --- | --- |
| `/dev/dma_heap/` does not exist | The kernel does not enable DMA-HEAP | Check the kernel configuration and rebuild the kernel |
| `shm_alloc()` returns a failure | Insufficient memory, or the heap does not support the requested attributes | Reduce the allocation size, or use a different heap |
| `shm_import_fd()` fails | The fd is invalid or already closed | Confirm the fd's source is correct and that it has not been closed |
| Cross-process transfer data is incorrect | The cache was not synced | Call `shm_sync_cache()` before and after the DMA transfer |
| `shm_trans_sub_recv()` times out | The publisher did not send data, or the socket disconnected | Check the publisher status and confirm the socket connection is normal |
| Socket connection fails | The socket file does not exist or permissions are insufficient | Confirm the publisher has started and check `/tmp/` permissions |

## Appendix: Performance and Test Data

| Metric | Value | Test Conditions |
| --- | --- | --- |
| Cross-process transfer latency | ~100 μs | 4 KB data frame, local Unix socket |
| Zero-copy throughput | ~2.5 GB/s | 1 MB data frame, continuous transfer |

```bash
# Terminal 2
./shm_transport_sub_test test --benchmark
```
