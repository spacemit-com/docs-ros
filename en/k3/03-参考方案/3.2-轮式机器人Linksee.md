# Linksee Wheeled Robot

## 1. Overview

- **Supported Features**:
   The `linksee` full-robot solution for the `k3-com260` board integrates **chassis motion control, odometry publishing, IMU support, 2D LiDAR support, person following, autonomous navigation, and multiple SLAM mapping capabilities**.
  Specifically:
  - The chassis layer enables `base`, which supports differential-drive velocity control, forwarding `/cmd_vel` commands to the chassis driver, and publishing [/odom](vscode-file://vscode-app/usr/share/code/resources/app/out/vs/code/electron-browser/workbench/workbench.html) odometry and TF;
  - The sensor layer enables the `IMU` and `Lidar` peripheral components, supporting the `CMP10A` IMU and `YDLIDAR` / `RPLIDAR` drivers;
  - The perception layer enables `person_follow`, which supports vision-based person following;
  - The planning and navigation layer enables `nav2`, which supports navigation using a 2D LiDAR or RGB-D camera;
  - The mapping and localization layer enables `cartographer_run`, `rtabmap_run`, and `slam_toolbox_run`, supporting multiple mapping and localization modes, including 2D LiDAR SLAM, RGB-D SLAM, and 3D point-cloud SLAM;
  - The AI application layer supports the `linkseeHost/linkseeClient` end-to-end control pipeline, covering teleoperation, data collection, ACT model training, deployment inference, and natural-language task triggering through `mlink gateway + MCP + Hermes`;
  - The application layer enables [linksee](vscode-file://vscode-app/usr/share/code/resources/app/out/vs/code/electron-browser/workbench/workbench.html), which provides ROS 2 application integration for the `linksee` product.

**Architecture:**

The following diagram shows the `linksee` software architecture:

![](./assets/linksee_ref_mars-framework.png)

`application/ros2/linksee` provides full-robot application integration. `middleware/ros2/planning/nav2` provides navigation. `middleware/ros2/slam/cartographer_run`, `middleware/ros2/slam/slam_toolbox_run`, and `middleware/ros2/slam/rtabmap_run` provide different mapping and localization modes. All these modules connect to the chassis control pipeline through `/cmd_vel`.

### 2.2 Bill of Materials

**3D-Printed Parts:**

Print the Linksee robot enclosure and chassis parts in advance. The 3D model files are available in the [spacemit-robotics/linksee-mechanical](https://github.com/spacemit-robotics/linksee-mechanical) repository, with the following structure:

```text
linksee-mechanical
├── LICENSE
└── step
  ├── chassis.step
  ├── cover.step
  ├── head.step
  ├── main_housing.step
  └── rear_enclosure.step
```

The 3D model files serve the following purposes:

| File | Part | Purpose |
| :-- | :-- | :-- |
| `step/chassis.step` | Chassis | The robot's bottom load-bearing structure. It mounts chassis-related components, including motors, wheels, casters/fixed wheels, the battery, and the driver board. |
| `step/main_housing.step` | Main housing | The robot's main enclosure. It secures the K3 controller, wiring harnesses, and internal electronics, and provides mounting support for upper structures. |
| `step/head.step` | Head | The robot's front/upper exterior part. It forms the Linksee head shape and provides mounting locations for sensors or forward-facing structures. |
| `step/cover.step` | Cover | A cover for the top of the main body or a service opening. It protects internal components and allows assembly and later maintenance. |
| `step/rear_enclosure.step` | Rear enclosure | The robot's rear enclosure. It protects rear wiring and internal components and completes the robot exterior. |

After printing, assemble the robot with the main components listed below, M4 self-tapping screws (15–20 mm), Dupont wires, and other accessories. Use the screws to connect the chassis, cover, and housing.

**Robot Arm Parts:**

The Linksee mobile-manipulation robot uses an [ARM101 follower arm](https://github.com/TheRobotStudio/SO-ARM100). For purchase reference, see the `SO-ARM100` link in the main bill of materials. To build the arm yourself, follow the [`SO-ARM100` repository](https://github.com/TheRobotStudio/SO-ARM100) documentation to prepare the ARM101 follower-arm parts, servos, and other materials.

**Note:** Connect the bottom-most arm servo directly to the housing. Remove any other components attached to that servo.

### 3.2 Software Environment: Auxiliary Core

Use `bianbu26 lxqt` version 4.0 or later. Use the firmware recommended in [Flash the Image](../02-快速入门/2.2-镜像烧录.md). Earlier versions do not support communication between the main core and auxiliary core.

**Replace the Auxiliary-Core ITB File**

```
sudo apt update && sudo apt install -y --allow-downgrades wget
su root && cd ~
wget https://archive.spacemit.com/ros2/prebuilt/esos_kernel/update_esos.sh
bash update_esos.sh
```

Non-root users must configure permissions:

```
sudo tee /etc/udev/rules.d/99-rpmsg.rules <<EOF
KERNEL=="rpmsg*", MODE="0666"
KERNEL=="rpmsg_ctrl*", MODE="0666"
EOF
```

```
sudo udevadm control --reload-rules
sudo udevadm trigger
```

After the replacement succeeds, power-cycle the development board. The auxiliary-core serial console displays the following output:

![](./assets/linksee_ref_esos-print.png)

It continuously prints encoder readings and wheel speed in millirevolutions per second.

## 9. Linksee End-to-End Inference

Building on the Linksee chassis, sensor, and navigation capabilities described in the previous sections, this section adds an end-to-end mobile-manipulation control solution. It covers data collection, model training, inference deployment, and the complete workflow for exposing inference as tools that trigger mobile-manipulation tasks through natural language.

### 9.1 Overview

This solution supports the following capabilities:

- **Communication and control**: Use a Host/Client architecture for Linksee robot control, observation collection, and remote communication.
- **Teleoperation**: Use an SO101 leader arm to control the Linksee arm and the keyboard to control the Linksee chassis for mobile-manipulation teleoperation.
- **Data collection**: Collect end-to-end datasets containing robot-arm, chassis, and multi-camera observations.
- **Model training**: Train an ACT model from the collected data, with support for resuming interrupted training.
- **Inference evaluation**: Deploy the trained model to the inference device and evaluate end-to-end inference on the Linksee robot.
- **Natural-language control**: Package the Linksee end-to-end inference workflow as a native application, register its capabilities as MCP tools through the `mlink device → mlink gateway → MCP` pipeline, and integrate them with the Hermes Agent framework so natural-language commands can control Linksee mobile-manipulation tasks.

The Linksee end-to-end control workflow uses a distributed Host/Client architecture:

![Linksee distributed architecture](assets/linksee-distributed-architecture.png)

- `LinkseeHost` connects to the Linksee robot, instantiates Linksee, and directly controls the arm and chassis.
  - The arm is controlled through the SO101 solution from LeRobot.
  - The chassis uses `LinkseeBaseAdapter` to connect to the SpacemiT Robot SDK `third_party/chassis` shared library.
- `LinkseeClient` sends teleoperation or inference data to `LinkseeHost`.
  - It sends actions through ZMQ.
  - It receives observations through ZMQ.

**`LinkseeHost` and `LinkseeClient` can run on the same device or on separate devices.**

### 9.2 Hardware Requirements

| Item | Details |
| :-- | :-- |
| Hardware/robot | Linksee mobile-manipulation robot |
| Training platform | Server with an RTX-series or newer GPU |
| Teleoperation and data-collection platform (optional) | PC |
| Inference platform | SpacemiT K3 development board with Bianbu v3.0+ firmware |
| Robot arm | SO101 leader arm, required for teleoperation and data collection |
| Visual input | Two USB cameras, named `front` and `wrist` in this example |
| Key peripherals and interfaces | The follower-arm serial port is typically `/dev/ttyACM0`; the chassis serial port is typically `/dev/ttyACM1`; cameras use `/dev/video*` |

Before running the workflow, verify the following:

- The Linksee arm, chassis, and USB cameras are connected to the K3 development board.
- The SO101 leader arm is connected to the PC during teleoperation and data collection.

### 9.3 Scenario 1: Linksee End-to-End Control

This scenario covers the complete Linksee mobile-manipulation workflow, from real-robot teleoperation and data collection through ACT model training and inference.

#### 9.3.1 Environment Setup

> [!NOTE]
>
> This scenario uses three code environments:
>
> 1. Teleoperation and data collection: Install the dependencies on both the PC and the K3 development board.
> 2. Training: Install the dependencies on the GPU server.
> 3. Inference evaluation: Install the dependencies only on the K3 development board.

1. Clone the repository

   ```bash
   git clone git@github.com:spacemit-robotics/lerobot.git
   ```

2. Install system dependencies

   ```
   sudo apt update

   sudo apt install ffmpeg

   sudo apt install -y \
     libavformat-dev \
     libavcodec-dev \
     libavdevice-dev \
     libavutil-dev \
     libavfilter-dev \
     libswscale-dev \
     libswresample-dev

   sudo apt install -y \
     build-essential \
     cmake \
     pkg-config \
     python3-dev
   ```

   - `python3-venv`: Used to create a Python virtual environment.
   - `ffmpeg`: Used for video-frame processing and dataset video encoding.

3. Install LeRobot dependencies

   Create a virtual environment and install the dependencies:

   ```bash
   cd ~/lerobot

   # Set the Python version to 3.12. Install the pyenv environment first by following Section 3.3 of "3.3.1 Real-Robot Training and Inference".
   pyenv local 3.12.13
   python3 -V

   # Create and activate the virtual environment.
   python3 -m venv ~/.lerobot-venv
   source ~/.lerobot-venv/bin/activate

   # Install the torch and wandb dependencies.
   pip install torch==2.7.1
   pip install torchvision==0.22.0
   pip install wandb==0.24.0
   pip install pyarrow==23.0.0

   # Install dependencies for LeRobot and LeKiwi/Linksee.
   pip install -e .
   pip install "lerobot[lekiwi]"
   ```

4. Build the Linksee chassis shared library

   On the LinkseeHost system, enter the repository and build the chassis shared library:

   ```bash
   cd ~/lerobot
   ./scripts/build_mars_chassis.sh
   ```

   The default output is:

   ```text
   third_party/chassis/build/libchassis.so
   ```

   If you do not use the default vendored library path, specify the absolute `.so` path with `--robot.base_control_library_path` when starting the Host.

5. Add the user to the `video` group for camera access

   ```bash
   sudo usermod -aG video $USER
   ```

   `USER` is the current system user. Sign in again for this change to take effect.

6. Identify the robot arm, chassis, and camera device indexes

   ```bash
   # List the robot arm and chassis device nodes.
   lerobot-find-port

   # List the camera device nodes.
   lerobot-find-cameras opencv
   ```

7. Grant read and write access to the robot arm and chassis devices

   ```
   sudo chmod 666 /dev/ttyACM*
   ```

8. Add the user to the `video` group for camera access

   ```bash
   sudo usermod -aG video $USER
   ```

   `USER` is the current system user. Sign in again for this change to take effect.

#### 9.3.2 Start LinkseeHost

On the LinkseeHost system, enter the repository:

```bash
cd ~/lerobot
source ~/.lerobot-venv/bin/activate
```

Start the Host:

```bash
python -m lerobot.robots.linksee.linksee_host \
  --robot.id=my_linksee \
  --robot.port=/dev/ttyACM0 \
  --robot.base_driver=drv_uart_esp32 \
  --robot.base_dev_path=/dev/ttyACM1 \
  --robot.base_baud=115200 \
  --robot.base_type=diff_2wd \
  --robot.base_left_wheel_gain=1.0 \
  --host.port_zmq_cmd=5565 \
  --host.port_zmq_observations=5566 \
  --host.connection_time_s=3600 \
  --robot.cameras='{
    "front": {"type":"opencv","index_or_path":"/dev/video15","width":640,"height":480,"fps":30,"fourcc":"MJPG"},
    "wrist": {"type":"opencv","index_or_path":"/dev/video13","width":640,"height":480,"fps":30,"fourcc":"MJPG"}
  }'
```

> [!TIP]
>
> 1. Replace `/dev/ttyACM0` and `/dev/ttyACM1` with the actual ports on your system.

## 10. Perceptive Grasping

`perceptive_grasp` is a closed-loop tabletop perceptive-grasping application for the Linksee wheeled robot. The system detects and segments targets from RGB-D images, generates top-grasp or side-grasp paths through depth back-projection, eye-to-hand calibration, and 3D geometric planning, and then drives the chassis, robot arm, and gripper to align, grasp, place, and recover safely.

The same pipeline supports three deployment modes:

| Runtime mode | Configuration files | RGB-D input | Execution backend | Deployment |
| --- | --- | --- | --- | --- |
| Linksee physical robot | `config/grasp_pipeline.yaml` | RealSense D435i or `spacemit_las2` | Linksee SO101, gripper, and chassis | K3 |
| Local MuJoCo on PC | `config/grasp_pipeline_mujoco_ur5e.yaml` and `config/grasp_pipeline_remote_mujoco_ur5e.yaml` | Virtual MuJoCo RGB-D camera | MuJoCo UR5e | Both the simulation service and pipeline run on the PC |
| Remote MuJoCo on PC/K3 | Same as above | Virtual MuJoCo RGB-D camera provided by the PC | MuJoCo UR5e on the PC | Service on the PC; pipeline on the K3 |

The system consists of the following modules:

- Perception input: RealSense D435i, `spacemit_las2`, or a MuJoCo backend, which outputs pixel-aligned color images, depth images, and camera intrinsics.
- Object detection: K3 uses `vision_service`, while the PC uses OpenCV DNN. Both run YOLOv8-Seg and output object classes, bounding boxes, and segmentation masks. Simulation configurations can also refine or supplement masks using instance colors.
- 3D estimation: `grasp_geometry`, which generates the target point cloud and estimates the tabletop plane, 3D dimensions, and horizontal principal axis.
- Task control: `grasp_pipeline`, which handles target association, strategy locking, re-perception after observation or chassis actions, execution orchestration, and failure recovery.
- Grasp planning: `grasp_planner` and `grasp_geometry`, which generate and validate top-grasp or side-grasp candidates.
- Robot-arm execution: `spacemit_manipulator`, `grasp`, or a MuJoCo executor, which performs approach, grasping, lifting, placing, homing, and failure recovery.
- Chassis alignment: `libchassis`, which adjusts the robot's position relative to the target.
- Voice interaction: `spacemit_audio`, VAD, ASR, and TTS, which receive commands and announce status.

This solution is intended for single-object grasping on a tabletop or in a close-range scene. Chassis assistance does not provide navigation, obstacle avoidance, or global path planning.

### 10.1 Overview

The perceptive-grasping pipeline is shown below:

1. **Perception input**: The stereo camera outputs color images, aligned depth, and camera intrinsics.
2. **Object detection**: YOLOv8-Seg outputs object classes, bounding boxes, and segmentation masks. The pipeline associates the same target across consecutive frames and waits for the target to become stable.
3. **3D estimation**: The geometric planner generates the target point cloud, fits the tabletop plane, estimates the target length, width, height, and horizontal principal axis, and performs an initial top-grasp or side-grasp classification.
4. **Closed-loop planning**: The pipeline locks the grasp strategy, moves to the corresponding observation pose, and detects the target again after the observation or chassis movement. Candidates must pass workspace, IK, joint-limit, tabletop-clearance, and complete-path checks.
5. **Robot-arm execution**: The Linksee arm performs approach, grasp, lift, placement, homing, and failure recovery in sequence.

Closed-loop planning also includes the following paths:

- **Chassis-assisted alignment**: When the target is outside the comfortable grasping zone, the chassis moves a short distance and stops. The pipeline then returns to target detection and reacquires color and depth data.
- **Voice interaction**: ASR sends grasping commands to the pipeline, and TTS reports the pipeline status.

- `X86_STANDALONE`: Enables host-side planning and debug builds on x86, using the OpenCV DNN detector and a mock executor. This mode does not control a real robot arm or chassis.
- `LAS2_RUNTIME_DIR`: Specifies a non-default `spacemit_las2` runtime directory. No setting is required when the runtime is under `~/las2_runtime`.

##### Configure the Grasp Strategy

`grasp.strategy` supports `auto`, `top`, and `side`. The release configuration uses `auto` to select a top or side grasp based on the target's 3D height, horizontal dimensions, and candidate reachability. It does not use the target class.

```yaml
grasp:
   strategy: "auto"
   top:
      approach_height: 0.10
      grasp_depth: 0.015
      gripper_offset: 0.0
      grasp_point_x_ratio: 1.0
      position_source: "mask_depth"
      safe_mask_interior: false
      support_plane_occlusion_recovery: false
      support_plane_height_anchor: false
      minimum_grasp_height: 0.0
      verification_lift_m: 0.0
      gripper_open: 0.6
   side:
      min_height_m: 0.060
      min_height_width_ratio: 1.0
      approach_distance_m: 0.020
      entry_clearance_m: 0.030
      pregrasp_min_x_m: 0.270
      single_sided_gripper: true
      gripper_offset_m: 0.010
      grasp_forward_offset_m: 0.020
      grasp_height_ratio: 0.60
      initial_lift_m: 0.050
      lift_retreat_m: 0.025
   gripper_effort: 0.8
   gripper_hold_load_threshold: 100.0
   gripper_empty_position_margin: 0.03
   gripper_timeout_ms: 3000
   geometry:
      sample_stride: 2
      max_object_points: 4000
      min_object_points: 80
      plane_distance_threshold_m: 0.008
      table_clearance_m: 0.005
      footprint_padding_m: 0.005
      gripper_max_width_m: 0.10
      planning_timeout_ms: 750
      perception_budget_ms: 500
   workspace:
      x_min: 0.0
      x_max: 0.5
      y_min: -0.3
      y_max: 0.3
      z_min: 0.0
      z_max: 0.20
```

- `top` parameters affect only top grasps, and `side` parameters affect only side grasps. The two groups do not override each other.
- `side.min_height_m` and `side.min_height_width_ratio` together define the 3D-shape threshold for initially selecting a side grasp in `auto` mode.
- `side.entry_clearance_m` controls the safety distance between the gripper's lower edge and the target's highest point as the arm enters the side-grasp area from the observation pose.
- `side.approach_distance_m` defines the horizontal feed distance from the pre-grasp pose to the grasp pose. `side.grasp_forward_offset_m` applies a forward/backward compensation to the complete side-grasp pose without changing the feed distance.
- `geometry` controls the target point cloud, tabletop plane, gripper width, and candidate-planning constraints.
- `geometry.perception_budget_ms` is the performance-warning budget. If the budget is exceeded, the system records `OVERRUN`; it does not terminate a safe candidate solely for exceeding the time limit.
- `workspace` is the safety boundary checked before robot-arm motion. Chassis alignment does not bypass workspace or IK checks.
- Gripper load and closing position are used together to determine whether the target was grasped.

#### 10.3.7 Run Grasping

**The following commands initialize real hardware. Commands other than `--plan-only` drive the robot arm and chassis. Before running, clear the robot workspace, verify that the emergency-stop and power-disconnect devices are available, and keep people away from the motion range.**

First, validate the configuration structure. This command does not initialize hardware:

```bash
./build/perceptive_grasp_core \
   --config config/grasp_pipeline.yaml \
   --validate-config
```

When the output contains `[Config] valid`, the configuration fields and values have passed validation.

First, use `--plan-only` to verify target perception, the grasp strategy, and the robot-arm path. This mode initializes the hardware and reads the robot-arm state, but does not send robot-arm or chassis motion commands:

```bash
cd ~/spacemit_robot/application/ros2/linksee/perceptive_grasp
source ~/spacemit_robot/build/envsetup.sh
./build/perceptive_grasp \
  --config config/grasp_pipeline.yaml \
  --target cup \
  --plan-only
```

After confirming that planning succeeds, perform actual grasping:

```bash
cd ~/spacemit_robot/application/ros2/linksee/perceptive_grasp
source ~/spacemit_robot/build/envsetup.sh
./build/perceptive_grasp \
  --config config/grasp_pipeline.yaml \
  --target banana
```

The application runs through the following workflow:

1. `detecting` associates the same target across consecutive frames and waits until the bounding-box position and area meet the stability criteria.
2. `planning` generates the target point cloud, fits the tabletop plane, and calculates top-grasp or side-grasp candidates. When the target position requires adjustment, the pipeline enters `base_aligning` and returns to `detecting` after the chassis stops.
3. After the target position meets the requirements, the pipeline locks the grasp strategy. Top grasping moves to `observe_joints`; side grasping moves to `side_ready_joints`.
4. After the observation motion completes, the pipeline refreshes camera data and performs detection and planning again. Images, depth, and 3D coordinates acquired before movement are not reused.
5. After candidates for the locked strategy pass workspace, gripper-width, joint-limit, IK, tabletop-clearance, and complete-path checks, the pipeline enters `approaching`.
6. A top grasp approaches downward from above the target. A side grasp first enters a safe pre-grasp pose from above the target, opens the gripper, descends, and then feeds horizontally.
7. `grasping` closes the gripper, `lifting` lifts or retreats, `placing` places and releases the target, and `homing` completes the current cycle.
8. After closing and lifting, the gripper uses position and load together to determine whether it is holding the target. If any stage fails, the pipeline enters `recovering`.

The chassis can intervene before strategy locking or during replanning after the observation motion. After every chassis action, the system reacquires images and depth. Once the strategy is locked, a single-frame depth fluctuation does not switch between top and side grasping.

For continuous grasping, add `--loop`:

```bash
./build/perceptive_grasp \
  --config config/grasp_pipeline.yaml \
  --target banana \
  --loop
```

`--loop` does not limit the number of cycles. After each cycle, the robot arm returns to the observation pose for that cycle's strategy and immediately begins the next detection cycle. Loop mode does not distinguish a target seen in a previous cycle, so any target in view that meets the target-class and stability requirements can be grasped again.

After pressing `Ctrl+C` once, the application waits for the current action to finish and safely homes the robot. Press `Ctrl+C` a second time only to force-terminate it if it cannot exit safely.

The application supports two logging modes:

- Default mode reports the start time, duration, and result for each stage, and prints a `PIPELINE SUMMARY` at the end.
- Add `--debug` when debugging third-party libraries, the camera, robot arm, or chassis driver.

```bash
./build/perceptive_grasp \
  --debug \
  --config config/grasp_pipeline.yaml \
  --target banana
```

#### 10.3.8 Start Voice Control

The voice bridge starts the grasping application and manages recording, VAD, ASR, TTS, and status announcements:

```bash
cd ~/spacemit_robot/application/ros2/linksee/perceptive_grasp
source ~/spacemit_robot/build/envsetup.sh
source ~/.venv-grasp/bin/activate
./build/perceptive_grasp \
   --voice-control \
   --config config/grasp_pipeline.yaml
```

The physical-robot configuration uses SenseVoice by default. To temporarily switch to Qwen3-ASR, add `--asr-backend qwen3_asr`; this option applies only to the current run and does not modify the configuration file:

```bash
./build/perceptive_grasp \
   --voice-control \
   --asr-backend qwen3_asr \
   --config config/grasp_pipeline.yaml
```

You can issue voice commands after the terminal shows the following logs:

```text
[VoiceBridge] Listening: ...
```

Supported commands include:

- "Grab a banana": Starts a single banana-grasping task.
- "Stop": Cancels the current task. If the gripper is not holding an object, the robot returns to the observation pose and continues waiting. If the gripper may be holding an object, the robot returns to the home pose and exits.
- "Finish" or "go home": Returns the robot arm to the home pose and exits the application.

### 10.4 Physical-Robot Acceptance and Logs

Complete at least one full-workflow acceptance run for each of the top-grasp and side-grasp targets. Each task should meet the following conditions:

- The RGB-D color image, depth image, and camera intrinsics initialize successfully.
- Planning starts after the target becomes stable. After observation or chassis movement completes, the system reacquires RGB-D data.
- The candidate passes workspace, gripper-width, joint-limit, IK, tabletop-clearance, and complete-path checks.
- The pipeline completes `APPROACHING`, `GRASPING`, `LIFTING`, `PLACING`, and `HOMING` in sequence.
- The robot lifts the target after the gripper closes and confirms that it is holding the target, then places it in the specified area.
- The final summary reports `result=SUCCESS`, with no transition to `RECOVERING` and no unhandled errors.

Use the default logs to verify stage durations and results:

- `[Init]`: Initialization results for the camera, detector, robot arm, and chassis.
- `[Stage N]`: State-machine stage, stage duration, and result.
- `[Action]`: Duration of robot-arm, gripper, or chassis actions.
- `[Timing] stage=PERCEPTION_PLANNING`: Per-cycle perception and planning duration, budget, and result.
- `PIPELINE SUMMARY`: Initialization, task, end-to-end duration, and final failure reason.

### 10.6 MuJoCo Simulation

`perceptive_grasp` supports running the simulation environment and grasping pipeline separately:

- The PC runs MuJoCo physics simulation, RGB-D rendering, and the third-person view window.
- The grasping pipeline can run on the same PC or on the K3.
- The PC and K3 use the `remote_mujoco` protocol to transfer color images, depth images, camera intrinsics, and robot-arm commands.
- When the pipeline runs on the K3, the board's microphone and speaker can be used for voice interaction.

The simulation environment has the following characteristics:

- The robot uses the UR5e and Robotiq 2F-85 models from MuJoCo Menagerie.
- The physical environment simulates gravity, friction, contact, and object motion.
- Before execution, the system checks robot-arm/table collisions, the complete path, and two-finger contact.
- The physical-robot and simulation modes share the same launcher, pipeline state machine, object detector, 3D geometric estimation, grasp planner, and voice bridge.
- The simulation configurations replace only the camera and robot-arm backends and disable chassis alignment. They do not change the default physical-robot execution path.

#### 10.6.1 Build the PC Simulation Service

The PC requires x86_64 Linux and a desktop session with OpenGL support. Install the windowing and rendering dependencies:

```bash
sudo apt update
sudo apt install -y libglfw3-dev libgl1-mesa-dev
```

Build the simulation service:

```bash
cd ~/spacemit_robot/application/ros2/linksee/perceptive_grasp
python3 scripts/prepare_mujoco_assets.py
cmake -S . -B build_mujoco \
   -DUSE_OPENCV_DNN=ON \
   -DUSE_MOCK_EXECUTOR=ON \
   -DENABLE_WEBRTC_AEC=OFF \
   -DENABLE_LAS2_CAMERA=OFF \
   -DENABLE_MUJOCO_EXECUTOR=ON \
   -DENABLE_REMOTE_MUJOCO=ON
cmake --build build_mujoco -j"$(nproc)"
ctest --test-dir build_mujoco --output-on-failure
```

CMake first searches for MuJoCo in `MUJOCO_DIR`, `/usr/local`, and `/opt/mujoco`. If it is not found, the build system downloads a fixed version and caches it in `~/.cache/thirdparty/mujoco`.

After the build completes, check the simulation service, scene resources, and pipeline program:

```bash
python3 scripts/check_runtime_env.py \
   --config config/grasp_pipeline_mujoco_ur5e.yaml \
   --build-dir build_mujoco \
   --skip-voice \
   --no-fix
```

The last line should be `[SUMMARY] ready`.

#### 10.6.2 Start the PC Simulation Service

```bash
./build_mujoco/perceptive_grasp \
   --serve-simulation \
   --config config/grasp_pipeline_mujoco_ur5e.yaml \
   --listen 0.0.0.0 \
   --port 9090 \
   --viewer
```

After startup, the service displays a third-person view window. The upper-right corner shows the virtual RGB-D camera view, whose downward-oblique pose covers the workspace.

The scene is initialized as follows:

- The widened green pickup zone is in front of the robot arm, and the red placement zone is to the right of the robot arm. They do not overlap.
- `apple`, `banana`, `cube`, and `cup` are dynamically arranged in a row based on their rotated occupied widths to prevent mutual occlusion.
- Each service startup or explicit scene reset randomly changes the arrangement order, positions, and horizontal placement angles. Changing the grasp target does not reset the scene.

The service prints the current object positions and `yaw` through `[MujocoSimulation] Pickup layout:`.

#### 10.6.3 Run the Pipeline Locally on the PC

After starting the simulation service, open a new terminal and run the same top-level launcher:

```bash
./build_mujoco/perceptive_grasp \
   --config config/grasp_pipeline_remote_mujoco_ur5e.yaml \
   --target apple \
   --remote-host 127.0.0.1
```

The local PC workflow connects to the simulation service on the same PC through the loopback address. Use it to check the scene, physical contact, collisions, and grasp-and-place actions. Object detection uses the OpenCV DNN backend in the PC build.

#### 10.6.4 Build and Run the K3 Client

Build the remote simulation backend on the K3:

```bash
cd ~/spacemit_robot
source build/envsetup.sh
cd application/ros2/linksee/perceptive_grasp
cmake -S . -B build_remote_mujoco \
   -DENABLE_REMOTE_MUJOCO=ON \
   -DENABLE_LAS2_CAMERA=OFF \
   -DENABLE_WEBRTC_AEC=ON
cmake --build build_remote_mujoco -j"$(nproc)"
```

Before running, check the current build, optional voice devices, and the PC simulation service:

```bash
source ~/.venv-grasp/bin/activate
python3 scripts/check_runtime_env.py \
   --config config/grasp_pipeline_remote_mujoco_ur5e.yaml \
   --build-dir build_remote_mujoco \
   --no-fix
```

Run grasping, replacing `<pc_ip>` with the PC's actual address:

```bash
./build_remote_mujoco/perceptive_grasp \
   --config config/grasp_pipeline_remote_mujoco_ur5e.yaml \
   --target apple \
   --remote-host <pc_ip>
```

`--target` supports `apple`, `banana`, `cube`, and `cup`. `--remote-host` and `--remote-port` override the remote camera and robot-arm addresses together.

Set `--target` to `apple`, `banana`, or `cube` to validate top grasping. Set it to `cup` to validate side grasping. The top-level `remote_mujoco` configuration block sets both the camera and robot-arm service addresses, while `--remote-host` and `--remote-port` override the shared endpoint for the current run.

#### 10.6.5 Use Voice Control for Simulation on the K3

First set `voice.asr.device_name`, `voice.asr.device`, `voice.tts.playback_device_name`, and `voice.tts.playback_device` in `config/grasp_pipeline_remote_mujoco_ur5e.yaml` based on device enumeration results, then run:

```bash
./build_remote_mujoco/perceptive_grasp \
   --voice-control \
   --config config/grasp_pipeline_remote_mujoco_ur5e.yaml \
   --remote-host <pc_ip>
```

The voice bridge runs VAD, ASR, AEC, and TTS locally on the K3. The pipeline reads the simulated camera and controls the UR5e through the same `remote_mujoco` endpoint. Voice commands are the same as for the physical robot, including grasp, cancel, and home commands.

Running MuJoCo locally on the K3 is outside the scope of this solution. MuJoCo physics simulation, OpenGL rendering, and the third-person view window remain on the x86_64 PC.

#### 10.6.6 Validate the Simulation Results

First validate both MuJoCo configurations on the PC:

```bash
./build_mujoco/perceptive_grasp_core \
   --config config/grasp_pipeline_mujoco_ur5e.yaml \
   --validate-config
./build_mujoco/perceptive_grasp_core \
   --config config/grasp_pipeline_remote_mujoco_ur5e.yaml \
   --validate-config
```

Both commands should output `[Config] valid`.

A complete task should meet the following conditions:

1. `apple`, `banana`, and `cube` select `top`; `cup` selects `side`.
2. The green pickup zone, red placement zone, and all four objects appear in the camera view without occluding one another.
3. The target moves with the gripper only after two-finger contact occurs.
4. The robot arm lifts the target and carries it above the red placement zone.
5. After the gripper opens, gravity drops the target onto the table, and the service reports `inside_zone_xy=true`.
6. The pipeline completes `APPROACHING`, `GRASPING`, `LIFTING`, `PLACING`, and `HOMING`, and the final summary reports `result=SUCCESS`.
7. During continuous grasping, placed targets remain inside the red zone, and selecting a later target does not reset the scene.

If the robot arm collides with the table, the complete path collides, the gripper closes without an object, communication times out, or the target lands outside the red zone, the task enters failure recovery. The program does not directly modify object coordinates to fabricate a successful grasp.

## 11. Troubleshooting

| Symptom | Resolution |
| :--- | :--- |
| `linksee` is not listed in `lunch` | Run `source build/envsetup.sh` to reload the build environment. Verify that the repository is fully synchronized and that the current directory is the `spacemit_robot` root. If necessary, run `repo sync -j4` again. |
| `m` fails because ROS 2 dependencies are missing | Reinstall the dependencies listed in the system-dependency section, including `ros-humble-nav*`, `ros-humble-cartographer*`, `ros-humble-pcl-ros`, and `ros-humble-robot-localization`. Open a new terminal and load the environment after installation. |
| The chassis node starts, but the robot does not move | Check whether `/cmd_vel` input is available. Run `teleop_twist_keyboard` for a minimal test, and verify the chassis controller, motor driver, and battery power. |
| The robot moves in the wrong direction | Check the left and right motor wiring and direction definitions. Also verify the wheel mapping, direction-control pins, and chassis parameters. |
| `/odom` has no data or is clearly incorrect | Check the encoder feedback path. Verify that the wheel diameter, wheelbase, gear ratio, and other parameters match the physical chassis. Recalibrate `wheel_base` and `reduction_ratio` if the odometry drifts significantly. |
| The LiDAR fails to start or no point cloud is visible during navigation | Verify that the LiDAR is connected through the correct USB/serial interface and recognized by the system. Rerun `ros2 launch linksee start_ydlidar.launch.py` and inspect the logs. Check the LiDAR power supply and model configuration. |
| Navigation does not work, or the map/localization is incorrect after starting `nav2` | First verify that the chassis `/odom`, LiDAR `/scan`, IMU, and other basic topics are publishing correctly. Validate mapping, localization, and navigation step by step instead of debugging `nav2` before the lower-level pipeline works. |
| The PC visualization does not show the robot, or the topic list is empty | Verify that the board and PC use compatible ROS 2 versions and can communicate over the network. Source the correct workspace on both systems, and check that `ROS_DOMAIN_ID` matches if necessary. |
| The chassis solution still does not work after replacing the auxiliary-core kernel or `itb` file | Verify that `update_esos.sh` and the kernel-replacement steps completed successfully, then reboot the system. Check the relevant device nodes and driver logs after startup. Reflash and test again if necessary. |
| Host cannot start the chassis | Verify that `./scripts/build_mars_chassis.sh` was run and that `third_party/chassis/build/libchassis.so` exists. |
| The follower-arm serial port cannot be found | Check the Linksee arm connection and verify that `--robot.port` points to the actual serial port, such as `/dev/ttyACM0`. |
| The chassis serial port cannot be found | Check the chassis controller connection and verify that `--robot.base_dev_path` points to the actual serial port, such as `/dev/ttyACM1`. |
| Insufficient serial-port permissions | Run `sudo chmod 666 /dev/ttyACM0` or `sudo chmod 666 /dev/ttyACM1` for the corresponding port. |
| Client cannot connect to Host | Verify that `remote_ip` / `REMOTE_IP` is the Host device IP and that firewall rules do not block ports `5565` and `5566`. |
| Camera frame rate is unstable or frames are dropped | Set `fourcc":"MJPG"` explicitly in `--robot.cameras` and verify that sufficient USB bandwidth is available. |
| A two-wheel differential-drive chassis cannot move laterally | This is expected behavior. A two-wheel differential-drive chassis does not support lateral movement. |
| Resumed data collection overwrites the old dataset | Set `RESUME = True` to append to an existing dataset. To create a new dataset, use a new `HF_REPO_ID` or remove the local data. |
| Training cannot be resumed | Verify that `--config_path` points to the existing checkpoint's `train_config.json` and set `--resume=true`. |
| The inference model path is invalid | Verify that `HF_MODEL_ID` points to an existing `pretrained_model` directory. |
| Gateway does not show tools after `linksee_device` starts | Verify that `mlink gateway` is running, the device name is `linksee`, and the startup command is `linksee_device unix linksee`. |
| Hermes cannot find the Linksee tools | Check that the MCP address in `~/.hermes/config.yaml` is `http://127.0.0.1:18765/mcp` and verify that `linksee_device` is connected to the gateway. |
| Natural-language inference startup fails because the model directory does not exist | Verify that the model is stored at `application/ros2/linksee/linksee_app/models/linksee_act_pick_place_move_v2/checkpoints/100000/pretrained_model`. |
| The robot arm is not released after stopping the Host | `stop_host.sh` first sends `SIGINT` to trigger Python cleanup. If the process does not exit before the timeout, the script falls back to forceful termination. Check `/tmp/linksee_host.log` for details. |
