# Building and Compilation

## 1. Prerequisites

Refer to [2.1 Power-On and Boot](./2.1-上电开机.md) and [2.2 Flashing](./2.2-镜像烧录.md).

### 1.1 Optional: Use Robot Skills to Assist with Environment Setup

When using a coding agent such as Codex, Claude Code, or Cursor, Robot Skills can be installed first to assist with SDK acquisition, dependency checks, board connection, development-mode selection, and build verification. Robot Skills is an optional aid and does not replace the manual commands described below.

Provide the repository URL directly in the agent chat to install Robot Skills:

```text
Please install https://github.com/spacemit-robotics/robot-skills
```

If installation through agent interaction is unsuccessful, install it manually:

```bash
# Codex
npx skills add spacemit-robotics/robot-skills --agent codex

# Claude Code
npx skills add spacemit-robotics/robot-skills --agent claude-code

# Cursor
npx skills add spacemit-robotics/robot-skills --agent cursor
```

Robot Skills selects a development mode according to the current scenario:

| Mode | Applicable Scenario | SDK Location | Build/Run Location |
| :--- | :--- | :--- | :--- |
| local | The agent runs directly on the development board | Development board | Development board |
| remote | The agent runs on a PC and accesses the development board through SSH | Development board; the SDK is not required on the PC | Development board |
| hybrid | Development on the PC; build and run on the development board | One copy on the PC and one on the development board; the default PC location is `~/workspace/spacemit-robot` | Development board |

In remote and hybrid modes, the agent logs in to the development board through SSH to check the SDK, install dependencies, build, and run. Robot Skills first checks whether passwordless login is already available based on the SSH target, port, private key, or local SSH configuration provided. If it is not configured, the agent guides the user to select an existing key or create a new key, then installs the public key on the development board. This process normally requires confirmation of the target address and may require interactive entry of the development board login password once in the terminal. The agent does not store passwords or request private-key contents in the chat.

For first-time use, after installing Robot Skills, provide the development board SSH address to the agent, such as Codex or Claude Code:

```text
The development board address is bianbu@10.0.90.29. Use hybrid development mode and help set up the SDK environment.
```

Before performing `sudo apt install`, `repo init`, `repo sync`, source configuration changes, or file synchronization, the agent should state the execution location and scope of impact, then wait for confirmation.

### 1.3 Optional: Install ROS 2 and Basic Dependencies Without the SDK

If the Robot SDK is not used and only ROS 2 is required, prepare a minimal ROS 2 environment as described in this section. When following the main Robot SDK workflow, skip this section and continue with [Section 2](#2-obtaining-the-source-code).

```bash
sudo apt update
sudo apt install \
  ros-humble-ros-base \
  ros-dev-tools \
  ros-humble-robot-localization \
  ros-humble-joint-state-publisher \
  ros-humble-tf-transformations
```

This minimal environment does not include RViz, Nav2, MoveIt, ros2_control, or other graphics- or hardware-related components.

Before using ROS 2 in a new terminal, load the Humble environment:

```bash
source /opt/ros/humble/setup.sh
```

## 2. Obtaining the Source Code

Download the complete Robot SDK repository source code as follows:

```bash
sudo apt update
sudo apt install repo git

# Configure the Git username and email address (the repo tool requires Git commit information)
git config --global user.name "Your Name"
git config --global user.email "you@example.com"

mkdir spacemit_robot
cd spacemit_robot

# Method 1: Use GitHub
repo init -u https://github.com/spacemit-robotics/manifest.git -b main -m default.xml \
  --repo-url=https://gitee.com/spacemit-robotics/git-repo
repo sync -j4
repo start robot-dev --all

# Method 2: Use Gitee
repo init -u https://gitee.com/spacemit-robotics/manifest.git -b main -m default.xml \
  --repo-url=https://gitee.com/spacemit-robotics/git-repo
repo sync -j4
repo start robot-dev --all
```

If only part of the source code is required, use the `-g` option with **repo init** to limit the groups, then run **repo sync**. For details, refer to [Section 5 Selective Download](#5-selective-download).

## 3. One-Command Build

This section uses the development board environment for building by default. To build in a PC environment, refer to the subsequent sections for Docker builds or cross-compilation.

```bash
cd spacemit_robot
source build/envsetup.sh
lunch  # Select the appropriate target
```

### 3.1 Full Build

```bash
cd spacemit_robot
m
```

### 3.2 Single-Component Build

```bash
cd component_directory
mm
```

After the build is complete, output artifacts are organized as follows: executables are located in `bin`, libraries in `lib`, header files in `include`, and configuration files in `share`.

The installation prefix for native and Docker builds is `output/staging`. Cross-compilation uses a separate output root, with an installation prefix of `output/cross/<target>/staging`; see [Section 3.5](#35-cross-compilation).

### 3.3 Selecting a Build Mode

The Robot SDK build system supports native builds, Bianbu Docker builds, and cross-compilation. All three modes use the same `lunch`, `m`, and `mm` commands, but differ in their execution environments and output directories.

| Mode | Applicable Scenario | Execution Environment | Relative Build Speed | Installation Prefix | Runtime Deployment Directory |
| :--- | :--- | :--- | :--- | :--- | :--- |
| Native build | Build on the development board or in a local environment with all dependencies installed | Current system | Slow on K1; moderate on K3 | `output/staging` | `output/rootfs` |
| Bianbu Docker build | Reproduce the Bianbu board environment as closely as possible or isolate system dependencies | Bianbu riscv64 Docker container | Slow | `output/staging` | `output/rootfs` |
| Cross-compilation | Generate riscv64 target artifacts on an x86_64 PC | Ubuntu host container and Bianbu sysroot container | Fast | `output/cross/<target>/staging` | `output/cross/<target>/rootfs` |

The table provides a qualitative comparison based on x86_64 PCs with comparable performance, package sets, and build parallelism. Actual build times also depend on CPU core count, memory, storage performance, `parallel_jobs`, cache hits, and initial container creation, image downloads, and sysroot preparation. Cross-compilation requires additional setup for the first build. Its speed advantage is more apparent when containers and sysroots are reused for subsequent builds.

The runtime deployment directory is generated automatically after a full `all` build. Running only `m -C`, `m -R`, or `mm` normally updates the installation prefix only. To generate the deployment directory, run `./build/build.sh deploy-rootfs`. For cross-compilation, run `./build/cross_build.sh deploy-rootfs`.

Docker builds and cross-compilation require Docker to be installed and the current user to have permission to run the `docker` command. Both modes must be explicitly enabled and are disabled by default after `source build/envsetup.sh`. Do not enable Docker builds and cross-compilation simultaneously in the same shell.

### 3.4 Docker Build

A Docker build runs the standard `build/build.sh` inside a Bianbu container that matches the target board; the external commands remain `m` and `mm`. Unlike cross-compilation, it uses the compiler, system dependencies, and ROS 2 environment provided by the Bianbu container.

For K3 targets, the default image is `bianbu:4.0`. If it is not available locally, the script attempts to pull `harbor.spacemit.com/bianbu/bianbu:4.0`. By contrast, K1 targets use `bianbu:2.3`.

Common workflow:

```bash
cd spacemit_robot
source build/envsetup.sh
lunch k3-com260-minimal

# Enable Bianbu Docker build in the current shell
m_enable_docker_build

# Full build
m

# Build only CMake / non-ROS2 packages
m -C

# Build only ROS 2 packages
m -R
```

Single-component Docker build:

```bash
cd spacemit_robot
source build/envsetup.sh
lunch k3-com260-minimal
m_enable_docker_build

cd components/peripherals/lidar
mm
mm --with-deps
```

Scripts or CI can also explicitly enable Docker builds for individual commands:

```bash
cd spacemit_robot
SROBOTIS_USE_DOCKER_BUILD=1 BUILD_TARGET=k3-com260-minimal ./build/build.sh all
SROBOTIS_USE_DOCKER_BUILD=1 BUILD_TARGET=k3-com260-minimal ./build/build.sh cmake
SROBOTIS_USE_DOCKER_BUILD=1 BUILD_TARGET=k3-com260-minimal ./build/build.sh package components/peripherals/lidar --with-deps
```

Common controls:

| Command / Variable | Description |
| :--- | :--- |
| `m_enable_docker_build` | Enables Docker builds in the current shell |
| `m_enable_docker_build disable` | Disables Docker builds in the current shell |
| `SROBOTIS_DOCKER_CONTAINER_NAME=srobotis-k3-build` | Specifies a fixed container name for reuse or troubleshooting |
| `SROBOTIS_DOCKER_PLATFORM=linux/riscv64` | Overrides the Docker platform; the default is `linux/riscv64` |
| `SROBOTIS_DOCKER_DEVICES=/dev/xxx` | Passes through `/dev/*` devices when host-device access is required |

Docker containers are reused by default based on the SDK path and Bianbu version. Docker builds do not create a separate `output/docker` directory. Instead, build intermediate files, logs, installation prefixes, and deployment directories are written to `output/` in the current source directory:

```text
output/
  build/     # CMake / ROS2 build intermediate files
  log/       # Build logs
  staging/   # Installation prefix; primary installation output of m / m -C / m -R / mm
  rootfs/    # Runtime deployment directory generated by m all or deploy-rootfs
```

Therefore, the runtime, packaging, and deployment paths after a Docker build are the same as those for a native build.

> **Note**
>
> - To switch from Docker builds to cross-compilation, first run `m_enable_docker_build disable`; conversely, to switch from cross-compilation to Docker builds, first run `m_enable_cross_build disable`.
> - Running `source build/envsetup.sh` again disables both Docker builds and cross-compilation. Therefore, re-run the appropriate enable command before continuing with either mode.

### 3.5 Cross-Compilation

Cross-compilation builds riscv64 target artifacts on an x86_64 PC through `build/cross_build.sh`. It uses an Ubuntu host container to run build commands such as CMake, colcon, and Cargo, and a Bianbu container to install target dependencies and export the riscv64 sysroot.

Common workflow:

```bash
cd spacemit_robot
source build/envsetup.sh
lunch k3-com260-minimal

# Enable cross-compilation in the current shell
m_enable_cross_build

# Full cross-compilation build
m

# Cross-compile only CMake / non-ROS2 packages
m -C

# Cross-compile only ROS 2 packages
m -R

# Clean cross-compilation output for the current target
m clean
```

Single-component cross-compilation:

```bash
cd spacemit_robot
source build/envsetup.sh
lunch k3-com260-minimal
m_enable_cross_build

cd components/peripherals/motor
mm
mm --with-deps
mm clean
```

Scripts or CI can call `cross_build.sh` directly without shell helper functions:

```bash
cd spacemit_robot
BUILD_TARGET=k3-com260-minimal ./build/cross_build.sh all
BUILD_TARGET=k3-com260-minimal ./build/cross_build.sh cmake
BUILD_TARGET=k3-com260-minimal ./build/cross_build.sh ros2
BUILD_TARGET=k3-com260-minimal ./build/cross_build.sh package components/peripherals/motor --with-deps
BUILD_TARGET=k3-com260-minimal ./build/cross_build.sh clean all
```

The cross-compilation output directories are:

```text
output/cross/<target>/
  build/                   # CMake / ROS2 build intermediate files
  log/                     # Build logs
  host/                    # Host-side tool prefix
  sysroot/                 # riscv64 target sysroot exported from the Bianbu container
  staging/                 # Cross-compilation installation prefix; primary installation output of m / m -C / m -R / mm
  rootfs/                  # Runtime deployment directory generated by m all or deploy-rootfs
  toolchain-riscv64.cmake  # CMake toolchain file
  meson-riscv64.ini        # Meson cross file
```

The cross-compilation dependency split can be checked without performing a build:

```bash
BUILD_TARGET=k3-com260-minimal ./build/cross_build.sh deps all
BUILD_TARGET=k3-com260-minimal ./build/cross_build.sh deps package components/peripherals/motor
```

After cross-compilation is complete, scan the ELF dynamic libraries in `staging` / `rootfs` to identify the apt runtime dependencies required on the development board:

```bash
BUILD_TARGET=k3-com260-minimal ./build/cross_build.sh runtime-deps all
```

Common controls:

| Command / Variable | Description |
| :--- | :--- |
| `m_enable_cross_build` | Enables cross-compilation in the current shell. Subsequent `m` / `mm` commands are redirected to `build/cross_build.sh` |
| `m_enable_cross_build disable` | Disables cross-compilation in the current shell |
| `SROBOTIS_CROSS_OUTPUT_ROOT=<dir>` | Overrides the default output directory, `output/cross/<target>` |
| `SROBOTIS_CROSS_REFRESH_SYSROOT=1` | Forces sysroot re-export; use after changing target dependencies and rebuilding |
| `SROBOTIS_CROSS_BIANBU_IMAGE=<image>` | Overrides the Bianbu sysroot image |

### 3.6 Adapting New Applications for Cross-Compilation

New applications are typically placed under `application/native/<app>` or `application/ros2/<app>`. For applications that use standard CMake or ament CMake, the build system automatically passes the riscv64 toolchain, sysroot, and installation prefix. In most cases, the application does not need to configure the cross-compiler again.

Complete the following configuration when adapting an application for cross-compilation:

1. Provide a `package.xml` for the application. Use `<depend>` to declare dependencies on components in the Robot SDK repository and `<system_depend>` to declare apt system dependencies.
2. Configure target dependencies, such as runtime libraries and header files, with `realm="target"`. These dependencies are installed in the Bianbu sysroot. If `realm` is omitted, system dependencies for applications and components also default to the target realm.
3. Configure code generators and build tools, such as `protoc`, `grpc_cpp_plugin`, `moc`, and Meson, with `realm="host"`. These dependencies are installed in the x86_64 Ubuntu host container.
4. Add the application path to `enabled_packages` in the target configuration. `mm --with-deps` builds the application and its SDK dependencies separately; `m` builds the complete package set for the target.

For example, a CMake application that depends on the `motor` SDK component, the protobuf target library, and host-side `protoc` can use the following `application/native/my_robot_app/package.xml`:

```xml
<?xml version="1.0"?>
<package format="3">
  <name>my_robot_app</name>
  <version>0.1.0</version>
  <description>My robot application</description>

  <depend>motor</depend>
  <system_depend realm="target" check_kind="pkg-config" check_arg="protobuf">libprotobuf-dev</system_depend>
  <system_depend realm="host" check_kind="command" check_arg="protoc">protobuf-compiler</system_depend>

  <export>
    <build_type>cmake</build_type>
  </export>
</package>
```

`<system_depend>` also supports the following attributes:

| Attribute | Description |
| :--- | :--- |
| `when="cross"` | Uses the dependency only during cross-compilation. `native` and `docker` can be used to exclude cross-compilation. |
| `realm="host\|target\|both\|skip"` | Specifies host tools, target sysroot dependencies, installation in both environments, or exclusion during cross-compilation, respectively. |
| `arch="riscv64"` | Uses the dependency only when the architecture of the current realm matches. |
| `check_kind` / `check_arg` | Specifies the dependency check method and its arguments. Supported values are `dpkg`, `command`, `pkg-config`, `file`, and `rustlib`. |

Then add the application to the target configuration:

```json
{
  "enabled_packages": [
    "components/peripherals/motor",
    "application/native/my_robot_app"
  ]
}
```

Check the dependency split before building an individual application:

```bash
BUILD_TARGET=k3-com260-my-robot ./build/cross_build.sh deps package application/native/my_robot_app
BUILD_TARGET=k3-com260-my-robot ./build/cross_build.sh package application/native/my_robot_app --with-deps
```

When an application's CMake project uses `ExternalProject_Add` to start a new CMake configuration process, the child project does not automatically inherit the top-level toolchain. Convert `SROBOTIS_CMAKE_EXTRA_ARGS` to a CMake argument list and pass it to the child project's `CMAKE_ARGS`. If the child project uses Meson, pass `--cross-file "${SROBOTIS_MESON_CROSS_FILE}"` to the Meson configuration command. For tools that must run during the build, explicitly use host-side executables. Do not attempt to run riscv64 programs from the sysroot.

## 4. Target Configuration

For the selected build target, enable or disable components and packages in the corresponding configuration file. To exclude a package, remove it from the configuration.

```bash
ls target/k3-*.json
```

Use `k3-com260-minimal.json` as an example:

```json
{
  "version": "1.0",
  "board": "k3-com260",
  "product": "minimal",
  "description": "K3 COM260 board - minimal build configuration",
  "enabled_packages": [
    "components/peripherals/imu",
    "components/peripherals/motor",
    "components/peripherals/lidar",
    "components/agent_tools/mlink_device",
    "components/model_zoo/vision"
  ],
  "enabled_package_options": {
    "components/peripherals/motor": { "enabled_drivers": ["drv_can_dm"] },
    "components/peripherals/imu": { "enabled_drivers": ["drv_uart_cmp10a"] },
    "components/peripherals/lidar": { "enabled_drivers": ["drv_uart_ydlidar", "drv_uart_rplidar"] },
    "components/peripherals/nfc": { "enabled_drivers": ["drv_i2c_SI512"] },
    "components/peripherals/pm": { "enabled_drivers": [] }
  },
  "options": {
    "parallel_jobs": 4,
    "auto_resolve_dependencies": true
  }
}
```

After modifying the configuration file, run `lunch <target>` again to select the target, then rebuild.

## 5. Selective Download

If the full SDK is not required, download only the required packages for the applicable scenario. Append the `-g` option to the end of the `repo init` command to specify the software package groups. Examples are as follows:

```bash
# Download only AI-related applications: Model Zoo + ai-gateway
repo init -u https://github.com/spacemit-robotics/manifest.git -b main -m default.xml \
  --repo-url=https://gitee.com/spacemit-robotics/git-repo \
  -g core,model_zoo,ai-gateway
repo sync -j4
repo start robot-dev --all

# Download only humanoid applications: complete humanoid package (humanoid + model_zoo_rl + simulation; see manifest component/simulation.xml for simulation)
repo init -u https://github.com/spacemit-robotics/manifest.git -b main -m default.xml \
  --repo-url=https://gitee.com/spacemit-robotics/git-repo \
  -g core,model_zoo_rl,humanoid,simulation
repo sync -j4
repo start robot-dev --all

# Download only desktop robot applications: Reachy mini
repo init -u https://github.com/spacemit-robotics/manifest.git -b main -m default.xml \
  --repo-url=https://gitee.com/spacemit-robotics/git-repo \
  -g core,peripherals,agent_tools,reachy_mini
repo sync -j4
repo start robot-dev --all
```

Available groups (`-g` is specified only with `repo init`; the subsequent `repo sync -j4` is the same as in [Section 2](#2-obtaining-the-source-code), followed by `repo start robot-dev --all`):

| No. | Scenario | `-g` to Append to `repo init` (at the end of the same init command in [Section 2](#2-obtaining-the-source-code)) |
| :--- | :--- | :--- |
| 0 | Full download | Do not add `-g` |
| 1 | Complete humanoid package | `-g core,model_zoo_rl,humanoid,simulation` |
| 2 | Specific humanoid model | `-g core,model_zoo_rl,humanoid_common,humanoid_unitree_g1,simulation` |
| 3 | Desktop Reachy mini | `-g core,peripherals,agent_tools,reachy_mini` |
| 4 | Wheeled Linksee | `-g core,ros2,linksee` |
| 5 | Voice-interaction Omni | `-g core,multimedia,model_zoo,agent_tools,omni_agent` |
| 6 | Model Zoo + ai-gateway | `-g core,model_zoo,ai-gateway` |
| 7 | Basic peripheral drivers | `-g core,peripherals,agent_tools` |
| 8 | Robot perception | `-g core,model_zoo,ros2_perception` |
| 9 | Robot peripherals | `-g core,peripherals` |
| 10 | Planning and control | `-g core,multimedia,model_zoo,control,ros2_planning,ros2_control` |

For complete group definitions, refer to the `groups="..."` attributes in the `.xml` files of the manifest repository. For fragment paths, refer to the include configuration in `default.xml`.

## 6. Common Issues

Invalid directory:

```text
[mm] ERROR: Not a valid package directory
[mm] Hint: Run mm from a directory with CMakeLists.txt, package.xml, or build.sh
```

The current directory is not a valid component directory. Verify that the directory contains one of the following marker files:

| Directory Marker | Build Logic | Supported Path Examples |
| :--- | :--- | :--- |
| **`CMakeLists.txt` exists** | Pure CMake build | `components/peripherals/motor`, `application/native/*` |
| **An executable `build.sh` exists** | Custom script build | Any subdirectory containing `build.sh` |
| **`package.xml` (ament) exists** | ROS2 (colcon) build | `middleware/ros2/*`, `application/ros2/*` |

## Appendix: Common Build Commands

After loading the environment and selecting a build target in the repository root, build commands can be used to generate example applications for each component.

| Scenario | Build Command | Clean Command | Description |
| :--- | :--- | :--- | :--- |
| Full build | `m` | `m clean` | Builds all components |
| Build CMake packages only | `m -C` | `m -C clean` | Skips ROS2 packages |
| Build ROS2 packages only | `m -R` | `m -R clean` | Skips CMake packages |
| Single-component build | `cd component_directory && mm` | `mm clean` | Builds the component in the current directory |
| Return to the repository root | `croot` | — | After execution in any subdirectory, changes to the SDK root directory. Used with the environment loaded by `source build/envsetup.sh`. |
